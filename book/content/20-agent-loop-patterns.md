# 第 20 章　Agent Loop 的通用模式

> 所有智能体都是"循环 + 决策"，差别只在决策函数长什么样。把这四种模式记住，你就不需要追新名词了。

## 引子

每隔一段时间就会冒出一批新名词。"反思式智能体""规划执行分离""分层任务网络""自我修正循环"——听上去一个比一个先进，文档里还会配上复杂的架构图。

把图拉开仔细看，会发现它们几乎都能归到四种基本结构之一。差别通常只在两个地方：**决策函数里放的是什么样的提示**，以及**循环的终止条件是怎么设计的**。

这个观察很有用，因为这意味着两件事。**第一，你不需要为每个新名词重新学习一遍架构。** 只需要认出"这是哪一种模式，加上什么变体"。**第二，模式的成败主要由控制设计决定，而不是由提示措辞决定。** 一个结构清晰的 ReAct 循环，比一个措辞精妙但终止条件含糊的自定义模式更可靠。

这一章把四种模式拆开讲，然后集中讲循环控制的四要素——这是所有模式共用的部分，也是实际项目里最容易出问题的地方。

## 模式一：ReAct——思考与行动交替

这是最基础也最常用的模式。每一轮循环里，模型先输出一段推理（"我现在知道什么，我接下来要做什么"），然后输出一个行动（调用某个工具），宿主执行后把结果回灌，进入下一轮。

**它的核心价值是把"推理"显式化。** 因为推理被写出来了，它就成了上下文的一部分，会影响后续的决策。这比"直接输出行动"更稳定——模型在写下"我需要先查订单状态"之后，下一步真的去查订单状态的概率会显著提高。

**关键设计点有三个。**

**第一，思考是否要暴露给用户。** 在面向终端用户的产品里，完整的内部推理通常不适合直接展示（噪音大、可能包含不该展示的中间判断）。但把它从上下文里彻底去掉又会损害推理质量。实用的做法是：**保留在上下文里，但在展示层过滤。** 这两件事是分开的，不要混为一谈。

**第二，一轮里允许多少个行动。** 允许一轮内并行发起多个工具调用，可以显著减少轮数（第 2 章讲过减少步数的价值）。但它对模型的规划能力要求更高，而且当这些调用之间有依赖时容易出错。经验做法是：**无依赖的调用允许并行，有依赖的强制分轮。**

**第三，推理的长度要控制。** 无限制的推理会迅速吃掉上下文预算。常见做法是设置"简单情况不要长篇推理"的引导，或者在上下文接近上限时对历史推理做压缩（第 21 章）。

## 模式二：Plan-Execute——先规划后执行

这个模式把循环拆成两个阶段：先让模型产出一个步骤计划（通常是一个有结构的任务列表），然后逐步执行，每完成一步就更新计划状态。

**它的核心价值是让整体结构在早期就确定下来。** 这在两个场景里有明显优势：一是任务需要多个步骤且步骤之间有依赖（比如"先取数据，再算指标，再生成报告"），提前规划能避免执行时走弯路；二是步骤之间没有依赖时，**规划出来后可以并行执行**，显著缩短总时长。

**关键设计点有三个。**

**第一，计划的粒度。** 太粗（"分析这家公司"）等于没规划；太细（把每一步的提示都写出来）会僵化，一旦实际执行与预想不符就要重规划。合理的粒度是"**一个可被单独验证完成的动作**"。

**第二，重规划触发条件。** 执行过程中一定会遇到与计划不符的情况。必须明确"什么条件下重新规划"（某一步失败、发现了计划里没考虑的信息、剩余步骤明显不再适用），否则系统会僵化地执行一个已经不合适的计划。

**第三，计划的状态化。** 计划必须进入状态（第 11 章），每一步的完成情况也要被记录。这样中断恢复后才能知道"做到哪了"，也才能避免重复执行已完成的步骤。

**这个模式最常见的失败是"计划与执行脱节"：** 计划列得很好，执行时模型无视计划自由发挥。要解决它，需要在每一轮把"当前计划 + 已完成项 + 待办项"显式放进上下文，并要求执行必须对应到某个计划项。**没有这个显式对照，规划环节就只是浪费了一次调用。**

## 模式三：Reflexion——自我批判与重试

这个模式在执行完之后增加一个评估环节：让模型（或另一个模型）检查产出是否满足要求，不满足则给出具体问题，然后带着这些反馈重新执行。

**它的核心价值是有针对性的修正。** 相比于"失败就重试"（第 6 章），Reflexion 的重试带着**具体的失败原因**，因此修正的有效性高得多。

**关键设计点有三个。**

**第一，批判必须具体。** "回答不够好"是无效反馈，"回答中引用的订单号与提供资料中的不一致"才是有效反馈。**批判的质量决定了这个模式的价值**——笼统的批判只增加成本不改善结果。

**第二，必须有轮数上限。** 这是最容易失控的模式，因为"再改一次可能会更好"永远成立。必须有硬上限（通常两到三轮），并且要能检测"改动是否真的在改善"——如果两轮之间评估分数没有提升，就应该停止，而不是继续投入。

**第三，批判者与生成者是否分离。** 用同一个模型自我批判，容易产生"自我一致性偏差"（倾向于认为自己做得对）。用不同的模型或不同的提示视角（比如专门扮演挑错者）效果更好。这一点与第 18 章讲的评委偏差是同一个问题。

## 模式四：Router / Dispatcher——分类后分发

这个模式在最前面加一个分类环节：判断当前请求属于哪一类，然后交给对应的处理路径。每条路径可以是完全不同的一套流程。

**它的核心价值是"用正确的上下文处理正确的任务"。** 不同类型的任务需要不同的指令、不同的示例、不同的工具。把它们混在一个提示里，会导致注意力被稀释、工具选择出错（第 15 章讲的动机一和二）。路由把这个问题从"如何写一个万能提示"变成了"如何准确分类"——后者通常容易得多。

**关键设计点有三个。**

**第一，分类的可判定性。** 分类标准要能用一段可判定的描述表达。如果分类依赖模糊的判断（"这是复杂问题还是简单问题"），分类本身就会不稳定。实用做法是**先用规则能判的用规则**（比如按输入来源、按字段特征），只有规则判不了的才交给模型。

**第二，未匹配的兜底。** 必须有"都不属于以上类别"的处理路径。缺少兜底会让请求被错误地塞进某个类别。

**第三，路由的稳定性。** 如果分类结果会抖动（同一个输入两次分类不同），用户体验会非常割裂。缓解方式是降低分类任务的难度（减少类别数、提供清晰定义）、以及在必要时固定采样参数。

**四种模式可以组合。** 常见的组合是"Router 在最外层（按任务类型分流）+ 每条路径内部用 ReAct 或 Plan-Execute + 关键路径上加 Reflexion 校验"。组合的原则是：**每增加一层，都要能说清它解决的具体问题**，否则就是在堆复杂度。

## 循环控制四要素

这一节是本章最重要的部分，因为**模式选对了但控制没做好，系统照样会失控。**

**要素一：终止判据。** 必须显式定义"什么叫做完成了"。三种终止方式都要有：

- **目标达成**：模型判断任务已完成（但这一条不可单独依赖，需要配合校验）；
- **情况明确**：任务无法完成（缺信息、超出能力、外部条件不满足）——**这一条最容易被遗漏**，没有它，模型遇到做不到的事会一直试下去；
- **约束触顶**：步数、成本、时间任一超限。

**"无法完成"必须是一个合法的终止状态。** 很多系统的设计里只有"成功"和"还在跑"两种状态，导致无法完成的任务会一直消耗预算。让"明确失败"成为一个正常出口，是一个重要的设计决定。

**要素二：预算。** 四类预算：步数（循环次数）、工具调用次数、token 用量、墙钟时间。**步数预算是必须的**，因为它是最直接防止无限循环的手段，而且它的消耗是确定的、可预测的。

**要素三：进展检测。** 这是四要素里最容易遗漏、也最有价值的一项。它的作用是识别"看起来在动，实际上在原地打转"。

实现方式有三种：**单调性检查**（某个体现进展的指标——比如已完成事项数、新增信息量——是否还在增长）；**重复检测**（同样的动作或同样的状态是否已经出现过）；**差异检查**（这一轮的输出与上一轮相比有没有实质区别）。

判断标准很实用：**如果一个循环连续两轮都没有产生新的信息，第三轮几乎不可能产生。** 这时应该终止或换策略，而不是继续投入。

**要素四：护栏。** 四类护栏在第 15 章讲过（预算型、收敛型、权限型、审批型），这里是它们在单智能体上的对应：**权限护栏**（限制哪些工具可调、调用频次上限）、**内容护栏**（输出前检查是否包含不该出现的内容）、**重复副作用护栏**（幂等键，第 13 章）、**人工闸门**（不可逆动作前确认）。

**把四个要素放在一起，可以得到一个反直觉但重要的结论：一个优秀的循环，关键不在"让模型更聪明"，而在"让失败更快地被识别并终止"。** 因为模型的能力你很难控制，而失败模式的可控性完全在你手里。一个能快速识别"这条路走不通"的系统，实际表现会明显好于一个"更聪明但会一直试下去"的系统。

## 从提示工程到控制流工程

这一章背后有一个范式转变值得点出来。

**早期的重心是提示工程**：如何措辞、如何组织示例、如何引导模型输出想要的内容。它的隐含假设是"只要提示写得好，模型就会做对"。

**现在的重心是控制流工程**：如何组织循环、如何设定终止条件、如何分配预算、如何检测无进展、在哪里插入人工闸门。它的隐含假设是"模型的不确定性无法消除，只能被约束"。

两种重心的差异可以列成一张对照表：

| 维度 | 提示工程 | 控制流工程 |
|---|---|---|
| 主要工作 | 措辞、示例、输出格式约束 | 循环结构、终止条件、预算分配、进展检测 |
| 隐含假设 | 提示写得好，模型就会做对 | 不确定性无法消除，只能被约束 |
| 典型失效 | 输出不稳定、格式漂移 | 长任务失控、预算被吃光、原地打转 |
| 随模型升级 | 收益递减，不同提示的差距在缩小 | 收益递增，模型越自主，约束越关键 |
| 可复用性 | 换模型往往要重写 | 结构可原样保留 |
| 排查入口 | 读提示找措辞漏洞 | 读轨迹看控制在哪一步失效 |

这张表最实用的一列是"随模型升级"。**它解释了为什么很多团队的经验传承不起来**：如果几年积累下来的资产主要是提示词，那么换一次模型就要重新积累一次；如果积累下来的是控制结构，那么模型升级对它是加分而不是清零。

这个转变的原因很实在：**随着模型变强，提示措辞带来的差异在缩小**（简单任务上不同提示的差异越来越小），而**控制结构的差异在放大**——一个没有终止判据的系统在长任务上必然失控，无论提示写得多好。

更实际的一点是：**控制结构是可复用的资产，提示措辞不是。** 换模型后提示往往要重写，而一个设计良好的循环结构（状态、终止判据、预算、进展检测）可以原样保留。所以投入在控制结构上的时间，比投入在措辞上的时间折旧更慢。

## 常见误区与排查

- **"循环转不动就加长提示，把规则写得更细"** → 症状：提示越写越长，行为改善有限甚至变差。根因：问题在控制结构而不在措辞。修法：先检查终止判据、预算、进展检测是否具备。
- **"模型自己会判断什么时候结束"** → 症状：偶发的长时间运行，或者过早收敛。根因：终止判据隐含在模型行为里。修法：把终止条件外部化，至少加约束触顶和"无法完成"出口。
- **"重试总会改善结果"** → 症状：成本上升但质量不变。根因：没有检测改动是否真的在改善。修法：设轮数上限，并对"轮间是否有提升"做检查。
- **"规划了就一定会照着做"** → 症状：计划很详实，执行时完全偏离。根因：计划没有在每轮显式出现在上下文里、没有强制对照。修法：每轮把计划状态放进上下文并要求执行对应到计划项。
- **"分类路由能处理一切输入"** → 症状：部分请求被错误分类，行为莫名其妙。根因：缺少未匹配兜底。修法：加兜底路径，并对分类结果做置信度检查。
- **"把推理过程全展示给用户，显得更透明"** → 症状：界面噪音大，用户困惑。根因：混淆了"上下文里的推理"与"展示层的内容"。修法：上下文保留、展示层过滤，两者分开处理。

## 本章要点

- 四种基本模式：ReAct（思考行动交替）、Plan-Execute（先规划后执行）、Reflexion（自我批判重试）、Router（分类分发）。新名词大多是其变体。
- 每种模式都有自己的主要风险：ReAct 是推理膨胀与步数失控，Plan-Execute 是计划执行脱节，Reflexion 是轮数失控，Router 是分类抖动与缺兜底。
- 模式可以组合，但每增加一层都要能说清它解决的具体问题。
- 循环控制四要素：终止判据（含"无法完成"这个合法出口）、预算（步数必须设）、进展检测（易被遗漏且价值高）、护栏。
- 进展检测的实用判据：连续两轮没有产生新信息，第三轮几乎不可能产生。
- 关键结论：循环质量取决于"失败能否被快速识别并终止"，而非"模型是否更聪明"。
- 范式已从提示工程转向控制流工程；控制结构是可复用资产，提示措辞会随模型更换而折旧。

## 迁移视角：如果不用这个框架

这四种模式与具体技术栈无关，它们是"自动化决策循环"的通用形态。

**ReAct** 的结构与经典的"感知-决策-行动"循环、以及专家系统里的"推理-行动"循环同源。**Plan-Execute** 对应经典的"分层任务网络"规划。**Reflexion** 对应控制系统里的"带反馈的迭代"。**Router** 对应任何分类-分发的架构（前端路由、消息路由、工单分派）。这些模式在自动化领域已经存在了几十年，LLM 的加入改变的是"决策函数由什么实现"，而不是循环本身的结构。

有一组从控制论借来的经验特别适合移植到这里。

**第一，闭环比开环可靠。** 任何没有反馈机制的系统都会积累偏差。智能体里的"反馈"就是观察步骤与进展检测——没有它们，循环就退化成"盲目重复"。

**第二，要区分"偏差"与"扰动"。** 偏差是系统性的（模型总是倾向于做某件错事），扰动是随机的（偶发的接口失败）。两者的处理方式不同：扰动靠重试，偏差靠修改结构。**把它们混为一谈会导致"一直重试一个结构性问题"，这正是许多智能体失控的根源。**

**第三，终止条件必须是显式的。** 控制理论里，一个没有明确终止条件的控制器是不完整的。这个直觉在这里同样成立：**任何循环都应该能回答"它在什么条件下停止"，并且答案是外部的、可验证的，而不是"模型觉得可以了"。**

最后一条关于工程重心的结论值得带走：**在自动化系统里，"防止最坏情况"的收益通常高于"提升平均情况"。** 因为最坏情况的成本（失控的成本、错误的副作用、长时间的不可用）远高于收益的边际改善。所以先做终止、预算、幂等、人工闸门这些防御性设计，再去优化提示与模型选择——顺序反了，就会在一个不稳固的基础上持续投入优化。
