# 第 3 章　框架抽象的本质：把什么变成接口

> 好抽象只做一件事：把"会变的实现"和"不变的契约"分开。判断一个抽象是否值得，只需要三个问题。

## 引子

几乎每个用 LangChain 的人都会经历一个怀疑时刻。

第一次读到这段代码结构的描述时，你会觉得它有点绕：为什么要给提示模板、模型、解析器都套上同一个"可运行"的外壳？直接把字符串拼好发出去不是更直接吗？

然后在某一天，你想把模型从一家供应商换到另一家，或者想把检索器从向量库换成关键词匹配，或者想在不改动业务逻辑的前提下加一层缓存、加一层日志、加一层重试。你发现只需要替换一个组件，其余部分完全不用动。

那一刻你会意识到：那个"多余的外壳"的作用，不是让你写得更短，而是让你**改动的影响范围可控**。这就是抽象的全部意义。

但抽象也有反面。LangChain 一路演进的过程中，有相当一部分抽象被推翻、被废弃、被标记为不推荐。它们的诞生和死亡遵循同一个规律。这一章要给出判断抽象的判据，并用这个判据去解释那些失败案例。

## 抽象在做的事：分离变化的实现与稳定的契约

把抽象的定义说得再实在一点：**抽象是在两个位置之间插入一层，使得一侧的变化不会波及另一侧。**

在没有抽象的世界里，业务逻辑直接调具体实现。于是会出现这样的耦合：业务逻辑知道"如果用的是 A 家模型，历史消息要按某种格式组织；如果换成 B 家，要按另一种格式组织"。这个知识污染了业务逻辑，导致换供应商变成一次重构。

有了抽象之后，业务逻辑只依赖"消息序列 + 生成参数"这个契约；每家供应商的格式差异，被收敛到适配层内部。变化被关在了一个盒子里。

这里有一个关键取舍必须讲明：**抽象会把"简单的事情"变复杂，把"复杂的事情"变简单。** 如果你只有一个组件、一种用法、永不替换，抽象纯粹是负担。抽象的价值随"变化点的数量"和"实现的数量"增长。这就是为什么小型脚本不用框架是对的，而生产系统用框架也是对的——它们站在这个曲线的两侧。

## 抽象三判据

判断一个抽象值不值得引入，问三个问题。这三个问题可以套用到任何框架、任何语言，是本章最有迁移价值的部分。

**判据一：可组合吗？** 抽象之后的组件，能不能自由拼接出新结构，而不需要为每种拼接写新的适配代码？检验方法很简单：如果存在 N 个组件，它们之间是否都能两两任意组合且不需要胶水代码？如果某些组合需要特殊处理，说明抽象漏了东西。

**判据二：可替换吗？** 换个实现，调用方需要改多少？理想情况是零改动——因为调用方只依赖契约。如果换个实现需要改三处、加两个判断分支，那说明这个抽象的边界划错了。

**判据三：可观测吗？** 执行过程中，外部有没有一个统一的挂点，能看到"谁在什么时候以什么输入被调用，输出了什么"？这一条最容易被忽略，却最重要。一个不可观测的抽象，在出问题时等于一堵墙；而一个可观测的抽象，能把调试从"读框架源码"变成"看轨迹"。

| 判据 | 检验问题 | 不通过的症状 |
|---|---|---|
| 可组合 | N 个组件能否自由拼接而不写适配代码 | 出现大量只做参数转换的中间层 |
| 可替换 | 换实现需要改调用方吗 | 调用方出现供应商名称、格式判断 |
| 可观测 | 是否有统一的执行钩子能拿到每一步的输入输出 | 排查问题必须加临时打印再重新部署 |

用这三条去审视 LangChain 的 Runnable 协议（第 5 章），你会发现它三个都满足：统一的输入输出契约解决了可替换，组合子解决了可组合，回调机制解决了可观测。这也是它能活到今天的原因。

## 契约先于实现：为什么一切都要 Schema 化

在第 2 章的概率性约束下，契约不是文档，而是**运行时强制**。

LangChain 生态里有一套非常彻底的契约化设计：模型输出的结构、工具的参数、图的状态，全都有显式的类型定义。这不是为了代码好看，而是因为在这个环境里，"约定"没有约束力。

把契约化拆成三层来看：

**第一层，结构契约。** 声明一个数据应该长什么样——有哪些字段、什么类型、哪些必填。它的价值在模型侧体现为"约束生成"，在宿主侧体现为"拦截非法结果"。

**第二层，行为契约。** 声明一个组件接受什么、产出什么、失败时如何表现。这是 Runnable 协议做的事情。行为契约的关键在于**失败语义也被纳入契约**——不只是"正常返回什么"，还包括"出错时向上抛什么、能不能被回退替代"。

**第三层，语义契约。** 声明字段含义和单位。这一层最难，也最容易被跳过：`amount` 是元还是分？`deadline` 是绝对时间还是相对时间？这类歧义不会引发异常，只会引发沉默的错误。它们必须在 Schema 的字段描述里被写清楚，否则模型会按自己的理解填。

一个实用的度量：**看一个 LLM 系统是否成熟，就看它有多少处依赖"模型的自觉"，而不是依赖显式契约。** 数量越多，越脆弱。

## 控制反转：框架接管了执行循环

引入框架意味着一次控制权的转移：你不再是"写代码调用组件的人"，而是"提供组件、由框架来调用的人"。

这个转变在抽象层面上是有正当理由的：执行循环里包含了大量通用但易错的逻辑——顺序控制、并发调度、失败重试、状态合并、流式转发、钩子触发。如果每个项目各写一遍，等于让每个人重新解决同一批边界问题。

但控制反转有明确的代价，必须在设计时心里有数。

**代价一：调试路径变长。** 出错时错误栈里会夹杂大量框架内部帧。缓解办法是充分使用框架提供的观测钩子，把排查从"顺调用栈"转为"看执行轨迹"。

**代价二：默认行为成为隐性依赖。** 很多项目的正确性建立在"框架默认值正好是我想要的行为"上。一旦升级版本默认值变化，问题会突然出现。缓解办法是把依赖的默认行为显式化——即使框架支持默认，也在你的声明里写出来。

**代价三：逃生舱口的质量参差。** 当框架的抽象无法表达你的需求时，你需要一条退路（比如直接调用底层接口、或把某个环节换成自定义实现）。评估框架时，"逃生舱口是否干净"是一个重要的隐性指标。一个没有逃生舱口的框架，抽象泄漏时会把你困住。

## 抽象泄漏：那些被推翻的设计

LangChain 早期的一些抽象之所以被放弃，原因高度一致：**它们在错误的层级上做假设。**

**失败类型一：把"流程"硬编码成类。** 早期版本的很多链（Chain）是"有名字的具体流程"——比如问答链、摘要链、SQL 查询链。问题在于：流程是业务的表达，而业务流程千变万化。把流程做成类，结果是类的数量爆炸，且每个类只覆盖一种形状。用户的需求稍微偏一点，就只能绕过这个类自己写。这是典型的"抽象层级过高"——它把本应由用户组合的东西预先组合好了。

后来的解决方案是把组合能力下放：不提供"某某链"，而提供"组合这些零件的语法"。这是一个方向性的修正：**框架应该提供原子和组合规则，而不是提供成品。**

**失败类型二：把"执行"和"编排"混在一起。** 有些抽象既描述了做什么，又承担了怎么执行，还管着状态在哪。结果是想换执行方式（比如从同步换成异步）必须换掉整个抽象。这违反了可替换判据——变化点没有和被变化的部分分离。

**失败类型三：把"不确定的接口"当成稳定契约。** 有些抽象封装了模型提供的特定能力（例如某种特定格式的工具调用），并在自己的接口里承诺了这个行为。当模型供应商调整行为时，这层抽象就漏了。正确做法是把不稳定能力纳入统一契约的"可选能力"部分，并声明降级路径。

这三类失败的共同教训是本章的核心命题：**抽象应该封装"变化"，而不应该封装"选择"。** 供应商差异会不断变化，应该封装；"用户想要一条怎样的流程"是选择，不应该被框架预先决定。

## 抽象自检清单

在引入或设计一层抽象前，逐条过一遍：

- 这层抽象隔离的"变化点"是什么？能具体说出两个以上会变化的具体实现吗？
- 调用方是否只依赖契约，不出现任何实现细节（供应商名、格式名、字段专有名词）？
- 组合是否自由？有没有出现"只在这一对组合时才需要特殊处理"的情况？
- 是否有统一的观测挂点？能不能在不改业务代码的前提下拿到每一步的输入输出？
- 失败语义是否在契约内声明？回退、重试、超时是抽象的一部分还是散落在各处？
- 隐式依赖的默认行为有哪些？是否已显式声明？
- 逃生舱口在哪里？当抽象表达不了需求时，退路是什么？
- 这层抽象覆盖的使用场景是否足够多？如果只有一两个调用点，是否可以暂缓？

## 常见误区与排查

- **"抽象越多越专业"** → 症状：一个简单流程被拆成七八层，改一行要动四个文件。根因：为不存在的变化点准备了抽象。修法：用"这个位置未来会换实现吗"做准入判断，答案是"不确定"就先不抽象。
- **"把常用的流程预置成组件，用户会更省事"** → 症状：预置组件与真实需求总有偏差，用户被迫绕开或复制粘贴改造。根因：混淆了"原子"与"成品"。修法：预置组合示例，而不是预置组合结果。
- **"有默认值就不必显式声明"** → 症状：升级后行为变化，问题难以定位。根因：默认行为成了隐性依赖。修法：凡是影响正确性的参数，一律显式声明。
- **"出错时加打印看就行"** → 症状：线上问题无法在生产环境排查，只能本地复现（而概率性系统本地复现不了）。根因：抽象缺少观测挂点。修法：把观测当作抽象的必备能力，而不是事后补丁。
- **"契约是文档的事，代码里写不写无所谓"** → 症状：模型偶发填错字段语义，系统静默出错。根因：语义契约缺失。修法：在字段描述中写明含义与单位，并让校验层检查。

## 本章要点

- 抽象只做一件事：把会变的实现与不变的契约分开，让变化的影响范围可控。
- 抽象的价值随"变化点数量"和"实现数量"增长；单组件、不替换的场景引入抽象是负担。
- 三个判据贯穿全书：**可组合、可替换、可观测**。任一不通过，抽象就不可靠。
- 契约在 LLM 系统里必须是运行时强制，分为结构、行为、语义三层；语义层最容易被跳过，也最容易引发静默错误。
- 控制反转是框架的必然代价：调试路径变长、默认行为成为隐性依赖、逃生舱口质量参差。
- 抽象失败的根因高度一致：在错误的层级做假设。框架应提供原子与组合规则，而不是预置成品。
- 抽象应该封装"变化"，不应该封装"选择"。
- 引入抽象前用八条自检清单过一遍，能挡掉大多数过度设计。

## 迁移视角：如果不用这个框架

这三条判据与框架无关，它是工程通识的一部分。你在设计数据库访问层、消息队列封装、HTTP 客户端时，用的是同一套逻辑：隔离变化、依赖契约、留出观测口。

区别在于 LLM 应用里的"变化"更剧烈——第三方模型的接口行为会变，模型能力会变，甚至最优的编排形状都会随模型变强而变。这意味着一件事：**在 LLM 生态里，抽象的保质期比传统后端短。** 因此选择抽象时要额外权衡两件事：一是这层抽象依赖的能力有多不稳定（依赖越不稳定，越要留降级和绕过路径）；二是迁移成本有多高（越是复杂抽象，替换成本越高）。

一个可靠的策略是：**把稳定性分层。** 最稳的是数据契约（Schema、状态结构），把精力花在这里，因为它跨框架通用；中间层是执行语义（统一调用协议），可以跟随社区共识；最上层是具体编排形状与组件名称，这部分注定会变，所以不要让业务逻辑过度依赖它。这个分层思想，你在读完第三部分后会看得更清楚。
