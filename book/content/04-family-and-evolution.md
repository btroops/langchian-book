# 第 4 章　LangChain 家族的全景与演进脉络

> 读不懂这个生态，多半不是因为概念难，而是因为不了解它的版本史。每一层抽象的存在，都能在历史上找到一个具体的失败。

## 引子

在搜索框里打"LangChain 和 LangGraph 有什么区别"，你会得到三种互相矛盾的答案：一种说 LangGraph 是 LangChain 的替代品，一种说两者要配合使用，还有一种说这个比较本身就是错的。

三种答案都曾是对的，差别只在于它们截取的是哪个时间点。

2023 年的 LangChain 是"链的集合"，LangGraph 还不存在。2024 年两者并存，用哪个是一道选择题。2025 年 10 月两个库同时发布 1.0 版本，架构关系被明确下来：**LangChain 的智能体跑在 LangGraph 的运行时之上**。从那一刻起，"谁替代谁"这个问题就没有意义了——它们是同一套栈的上下两层。

这个例子里藏着一个通用教训：**在一个高速演进的生态里，"是什么"这个问题必须带上时间戳。** 所以这一章不讲"LangChain 是什么"，而是讲它为什么变成今天这样、每一步是被什么逼出来的。读完这一章，你再看这个生态里任何一个包，都能猜到它为什么存在。

**第一代：流程即类。** 最早的形态是把常见流程做成"有名字的组件"——问答、摘要、SQL 查询各有对应的类，通过参数声明式地拼装。它的优点是上手极快，缺点是第 3 章讲过的那个问题：流程是业务的表达，而业务流程千变万化。于是类的数量膨胀，而每个类的适用面都很窄，用户需求稍微偏一点就得绕开它。

**第二代：组合语言。** 修正方向是"不提供成品，提供原子和组合规则"。实现形式是一套统一的组件协议（Runnable）加上一种声明式的组合写法（LCEL）。这一代解决了两个问题：组件不再需要预先配对，组合能力下放给了使用者；执行语义统一，所以流式、批处理、异步这些能力对所有组合都自动成立。但它有一个硬边界——**它是无环的，表达不了循环**。

**第三代：显式状态机。** 智能体的核心是有环的控制流：根据中间结果决定下一步，可能回到之前的状态。这需要一个新的执行模型：状态在节点之间流动、条件边决定走向、并且在任意一步都能把状态保存下来。这就是 LangGraph 的起点。

值得记住的是演进的方向：**抽象层级先降低，再升高。** 第一代是高层的成品，第二代主动降低到原子层（更灵活但更啰嗦），第三代在原子之上重建了高层结构（有状态的图）。这个"降下来再升上去"的模式在技术演进里很常见——因为只有降到原子层并沉淀出统一协议之后，高层的重建才不会重蹈覆辙。

## 职责边界：谁负责什么

到 2026 年，这个生态已经形成了相对稳定的分层。理解这张表的办法是问两个问题：这一层管的是"组件"还是"执行"？它面向的是"开发期"还是"运行期"？

| 层 | 组件 | 职责 | 判断标准 |
|---|---|---|---|
| 契约层 | `langchain-core` | Runnable 协议、消息模型、提示与解析器、工具抽象 | 是否与具体供应商无关？是 |
| 高层开发层 | `langchain` | 标准智能体循环（`create_agent`）、中间件、结构化输出、内容块规范 | 是否提供"开箱即用的智能体"？是 |
| 低层运行时 | `langgraph` | 状态图、条件边、超步执行引擎 | 是否让你完全控制控制流？是 |
| 持久化 | `langgraph-checkpoint` 及后端包 | 检查点、线程、时间旅行 | 是否让执行可暂停、可恢复？是 |
| 适配层 | `langchain-openai` / `-anthropic` / `-ollama` 等 | 具体供应商实现 | 是否封装了单一供应商？是 |
| 兼容层 | `langchain-classic` | 早期链与旧式 AgentExecutor 的迁移保留地 | 是不是历史包袱？是 |
| 社区集成 | `langchain-community` | 大量第三方集成，质量参差 | 是否社区维护、迭代较慢？是 |
| 协议桥 | `langchain-mcp-adapters` | 把外部 MCP 工具转换成框架内的工具 | 是否在做协议转换？是 |
| 观测与评估 | LangSmith 及其 SDK | 追踪、数据集、评估、部署 | 是否跨框架可用？是 |

有几个判断对定位问题特别有用。

**`langchain-core` 才是"原理层"。** 协议、消息、解析器、工具抽象都在这里。绝大多数"为什么会有这个行为"的问题，答案在 core 而不在 `langchain`。而且这一层不依赖任何具体模型供应商，因此它的抽象最稳定，也最值得花时间理解。

**`langchain` 与 `langgraph` 的关系是"上层与运行时"，不是"新旧关系"。** 1.0 之后，`langchain` 提供的是一个**有立场的高层循环**（标准工具调用循环 + 中间件），而 `langgraph` 提供的是**没有立场的原语**（节点、边、状态）。当高层循环的默认行为符合你的需求时，用高层；当你要控制每一步时，下探到低层。两者共用同一套执行引擎，所以下探不会导致行为突变。

**兼容层是历史分界线。** 如果你手上的代码引用了 `langchain-classic`，说明它在用 1.0 之前的抽象。这类代码不是"错的"，但它和 1.0 的主线是两套心智模型，混用时最容易出现"同样的词指不同东西"的困惑。

## 为什么核心能力从 LangChain 迁到了 LangGraph

这件事值得单独讲，因为它是一次罕见的"框架自己承认层级不足"的案例。

迁移的根本原因是**职责错配**。早期的记忆抽象解决的是"把历史消息存起来再取出来"，这在单轮线性流程里够用。但它无法解决真正的问题：状态要在多个并发节点之间安全合并、要在任意一步被序列化保存、要在恢复时精确还原。这些是**运行时能力**，不是组件能力。把它们硬塞进组件层，结果就是组件层被迫承担它不该承担的复杂度。

同样的逻辑适用于智能体执行器：一旦执行涉及循环、并发、中断、恢复，它就变成了一个运行时问题，而运行时需要一个明确的状态模型。图是这个模型的自然选择。

这里有一个可以推广的判断：**当一类问题开始反复要求"跨步骤的、可持久化的、可恢复的"保证时，它就已经从组件问题变成了运行时问题。** 组件可以无状态、可以随时重建；运行时不行。这个判断标准在你自己做架构选型时同样适用。

几个依赖值得单独点出来，因为它们承担的是"原理性"职责：

**Pydantic 承担契约的物理实现。** 模型输出结构、工具参数、图状态，最终都落到它的校验机制上。理解 Pydantic 的校验语义（严格模式、类型强制、嵌套模型）就是理解这套框架的"边界在哪"。第 16 章会专门展开。

**token 计数库承担预算核算。** 上下文窗口是硬约束，那么"这段内容占多少预算"就必须可计算。这就是为什么 tokenizer 相关依赖是必需项而不是优化项——没有它，第 2 章讲的发送前核算就无法实现。

**重试库承担失败语义的底层实现。** 指数退避、抖动、异常白名单这些细节，框架不会重造轮子。理解这一层，你就能明白为什么"重试"在框架里的配置项长得像通用重试库的配置。

**加密与签名、模板引擎、YAML 解析**这些看起来无关的依赖，通常出现在两个地方：配置与密钥管理，以及提示模板的加载。它们的存在提醒一件事——**框架的依赖树反映了它必须解决的现实问题，而不只是它宣传的能力。**

## 一条不容易走弯的学习路径

基于前面的分层，有一条相对省力的路径：

**第一步，先把契约层吃透。** 理解消息模型（角色、内容块）、提示模板、输出解析器、工具抽象。这一层不依赖具体供应商，学会就稳定。

**第二步，理解执行语义。** Runnable 协议的四种执行模式、流式传播、失败语义与回退。这一步理解透了，后面所有"为什么这里能流式、那里不能"的问题都有答案。

**第三步，再进入图。** 状态模型、归约器、超步、检查点、中断。按这个顺序走，你会发现图不是一堆新概念，而是"把前两步的组件装进一个有状态的执行框架里"。

**第四步，最后才碰高层循环与中间件。** 高层抽象的价值在于省事，但如果你不懂它下面发生了什么，中间件的行为会显得像魔法。

反过来走的代价很具体：直接学 `create_agent` 的人，通常在需要自定义控制流时会卡住——因为他不知道那一步之下是状态图，也不知道状态图的节点和边在哪里可以介入。

这条路径有一个隐含前提：**每一步都值得停下来问一句"如果不这样会怎样"。** 只记结论的学习方式在这类生态上失效得特别快，因为这些抽象本身就是在回应具体的失败——离开失败场景去记它们，剩下的只是一堆名字。反过来，如果你知道每个概念出现之前人们踩的是哪个坑，那么即使这个包明天被重写，你也能在新包里认出同一个位置。

## 常见误区与排查

- **"LangGraph 是 LangChain 的替代品"** → 症状：纠结选哪个，或者在新项目里两者混用却说不清边界。根因：沿用 2024 年的认知，不知道 1.0 之后 LangChain 的智能体跑在 LangGraph 运行时之上。修法：把两者理解为同一栈的上下层。
- **"用了高层 API 就不需要理解状态图"** → 症状：需要自定义控制流（比如在某一步插入审批、或者失败后走另一条路）时无从下手。根因：高层循环默认行为之外的需求，必须下探到低层。
- **"看到一个包名就假设它的职责"** → 症状：把旧式链与新式图混在一起，出现"同名不同义"的困惑。根因：没区分契约层、高层层与兼容层。
- **"依赖越多说明框架越重，所以自研更轻"** → 症状：自研后发现重写了重试、序列化、token 计数、并发合并。根因：忽略了这些依赖在解决的都是必须解决的问题。评估自研时应当把这些成本计入。
- **"照着教程的顺序学就行"** → 症状：跟着教程能跑通，遇到真实问题不知道该看哪一层。根因：教程通常从高层 API 切入，而排查问题需要从契约层切入。

## 本章要点

- 生态里每一层抽象都能追溯到一个具体的失败，理解失败的顺序就理解了分层的顺序。
- 三代抽象的演进是"先降到原子层，再重建高层"：流程类 → 组合语言 → 状态机。
- `langchain-core` 是原理层，供应商无关、最稳定，最值得先投入。
- 1.0 之后 LangChain 与 LangGraph 是同一栈的上下层：上层给有立场的标准循环，下层给无立场的执行原语，共用同一套运行时。
- 核心能力从 LangChain 迁到 LangGraph 的根本原因是**职责错配**：当问题要求跨步骤、可持久化、可恢复时，它就是运行时问题而非组件问题。
- 兼容层的存在是历史分界线，混用最大的风险是"同一个词指不同东西"。
- 依赖族的选择反映了必须解决的现实问题：契约、预算核算、失败语义各自都需要底层支撑。
- 学习顺序应当是契约层 → 执行语义 → 状态图 → 高层循环与中间件。

## 迁移视角：如果不用这个框架

把这一章抽掉具体包名，剩下的是一个可复用的观察方法：**面对任何一个快速演进的框架生态，先找出它的"契约层"和"运行时层"分别在哪。**

契约层决定了你的代码能迁移多远——它通常最稳定，也最通用。运行时层决定了系统的行为边界——循环、并发、持久化、恢复这些能力都在这里。这两层的分界，往往就是"哪些知识会在三五年后依然有用"的分界。

另一个可迁移的结论是那个判断句：当一类需求开始要求跨步骤、可持久化、可恢复的保证时，它就从组件问题升级成了运行时问题。你在别处也会遇到同一个规律：批处理变成流处理时会遇到，脚本变成服务时也会遇到。识别这个升级点，是架构判断力里很重要的一项。
