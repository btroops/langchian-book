# 第 5 章　Runnable 协议：统一执行语义

> 一切都实现同一个接口，才可能自由组合。这个接口不是语法糖，它定义了"执行"这个词在这套框架里的确切含义。

## 引子

设想你手上有五类东西：提示模板、模型、输出解析器、检索器、自定义函数。你想把它们任意串起来。如果每一类都有自己的调用方式——模板要传字典，模型要传消息列表，解析器要传字符串，检索器要传查询和数量——那么每出现一种新的串联方式，你就得写一段转换代码。

五类东西两两组合是二十种情况；如果串联是三段，组合数还要再乘。这就是**适配爆炸**：系统复杂度随组件数量呈乘性增长，而增长出来的复杂度没有任何业务价值——它全部花在"把 A 的输出改成 B 能接受的样子"上。

解决这个问题的办法在软件工程里几乎只有一种：定义一套所有参与者都实现的统一协议。协议一旦统一，"怎么组合"就退化成了一个已经解决的问题。这一章讲的就是这套协议：它规定了什么、为什么必须包含这几项规定、以及这些规定带来了哪些代价。

## 统一协议的四要素

一个能承载自由组合的执行协议，必须规定四件事。缺任何一件，组合都会在某个场景下失效。

**要素一：输入输出的契约。** 每个组件声明它接受什么、产出什么。这一步的难点不在"声明"，而在"统一形状"——如果 A 产出的是字符串、B 接受的是字典，那么组合时就必须插入转换。因此协议通常约定一个**通用的数据形状**（比如"消息序列"），让所有组件在这条主线上对齐；同时允许组件在需要时接受更简单的输入（比如一个字符串），由协议负责把它提升到通用形状。

这个"提升"动作很关键。它让使用者不必每次都写完整结构，也让组合保持简洁：简单输入被自动规范化为通用形状，后续组件一律按通用形状处理。

**要素二：执行模式的枚举。** 同一个逻辑执行，可能有四种用法：单次（要一个结果）、批量（要一批结果）、流式（要逐步到达的结果）、异步流式（要逐步到达且不阻塞）。协议必须同时规定这四种形态，否则组合会在"某个组件不支持流式"这类地方断裂。

**要素三：配置与上下文的注入。** 执行时需要携带一些不属于业务数据的东西：超时、并发上限、回调、追踪标识、标签。协议必须提供一条**不污染输入输出**的通道来传递它们。如果把这些参数塞进输入结构，业务逻辑和运行时配置就会互相污染，而且组合时会被当成数据处理（这是很常见的 bug 来源）。

**要素四：生命周期的钩子。** 执行开始、结束、出错、重试这些时刻，必须能被外部感知。这条是第 3 章"可观测判据"的落地方式：**协议层就把埋点位置固定下来**，而不是让每个使用者自己在代码里撒打印语句。

| 要素 | 规定的内容 | 缺失后的症状 |
|---|---|---|
| 输入输出契约 | 通用数据形状 + 简单输入的提升规则 | 组合时需要大量转换适配代码 |
| 执行模式 | 单次 / 批量 / 流式 / 异步流式 | 想流式输出时必须重写链路 |
| 配置注入 | 与业务数据分离的运行时参数通道 | 配置混进输入，被当成数据传递 |
| 生命周期钩子 | 开始 / 结束 / 出错 / 重试的挂点 | 出问题只能靠加临时日志排查 |

## 四种执行模式的语义差异

四种模式不是"同一个东西的四种写法"，它们的语义差异是实质性的，理解这些差异能解释很多"为什么这里行为不一样"的困惑。

**单次执行**是最直白的：给一个输入，等一个输出。它的隐含语义是**原子性**——要么成功返回完整结果，要么抛错，没有中间状态可观察。这个语义在读代码时容易被忽略，但它决定了错误处理的写法：单次执行下，失败就是失败，你不会拿到"半个结果"。

**批量执行**的语义有两个容易踩坑的地方。第一，它是否保证顺序？通常结果顺序与输入顺序对应，但**执行顺序与完成顺序未必一致**。如果你的程序依赖"先发起的先完成"，就会偶发地出错。第二，它是否并发？并发度由配置决定，而并发又会和外部依赖的限制冲突（模型接口的速率限制、数据库连接池）。批量执行最常见的线上事故就是"批量把对方的限流打满"。

**流式执行**改变的是**结果的到达方式**，而不是结果的内容。它的语义关键在于：分片是增量交付的，每一片都是部分信息，最后一片才补齐全部内容。这带来两个推论：消费方必须能处理"暂时不完整"的中间态；而任何需要在完整结果上做的判断（比如校验、解析），必须等到流结束才能做。**流式与结构校验天然存在张力**——这是第 8 章要处理的问题。

**异步流式**是流式加上非阻塞。它的存在理由很直接：流式输出的最大用途是"边生成边展示给用户"，而展示通常发生在一个需要同时处理其他请求的服务里。如果流式是阻塞的，一个用户的长回答就会占住一个工作线程。所以在服务端场景，异步流式往往才是真正被需要的那个模式。

**为什么必须四种都有？** 因为它们是四个正交的需求维度：结果数量（一个还是一批）、结果到达方式（一次性还是增量）、阻塞方式（阻塞还是非阻塞）。少任何一格，使用者都要自己在外层补一层实现，而那一层实现无法参与协议的组合规则——也就是说，你精心组合的链路会在那个位置退化成一个不可组合的黑盒。

## 同步与异步的双轨代价

一个必须诚实面对的问题：为什么协议要同时维护同步和异步两套？只保留异步不是更干净吗？

答案是因为**使用场景的真实分布**。脚本、数据分析、教学示例这些场景天然是同步的，强制异步会显著提高使用门槛。而服务端、并发调度场景又必须异步。于是协议选择了双轨。

双轨的代价是真实的，主要有三条。

**代价一：实现两遍，行为可能漂移。** 一个组件要同时提供两条执行路径，两条路径的逻辑如果各写一遍，早晚会出现细微差异——比如同步路径没有处理某种异常，异步路径处理了。这类不一致极难排查，因为你在开发环境用同步跑得好好的，上服务就出错。

**代价二：混用引发隐蔽问题。** 在异步上下文里调用同步接口会阻塞事件循环；反过来，在同步代码里等待异步结果需要自己起循环，容易造成死锁或资源泄漏。这类问题的症状通常不是报错，而是"某个请求特别慢"，很难定位。

**代价三：调试路径分叉。** 两种执行路径的错误栈、断点行为、超时语义都不同，团队里需要维护两套排查经验。

实用的应对策略很简单：**在项目内统一选定一条轨道，不要混用。** 如果系统是服务，全异步；如果是批处理脚本，全同步。只在库的边界处做一次转换，并且把转换点明确标注出来。这条约定比任何优化技巧都更能减少这类故障。

## 回调：把可观测性钉在协议层

这是四要素里最不容易被重视、但在生产环境里价值最高的一条。

回调机制的形态是：协议在执行的关键时刻发出事件——组件开始、组件结束、组件出错、重试、流式分片到达。外部可以注册处理器，把这些事件收集起来。

它带来三个别的做法给不了的能力。

**第一，统一的观测点。** 因为所有组件都实现同一协议，所以一个回调处理器可以覆盖整条链路，不需要每个组件分别适配。这直接决定了"加一个追踪能力"的成本：在协议层做，成本是一处；在业务层做，成本是每一处。

**第二，父子关系的自动建立。** 因为协议知道"谁调用了谁"（组合关系是协议的一部分），它可以自动构造出执行树：一次根调用下面挂着哪几次模型调用、哪几次工具调用、各自耗时多少。这正是第 18 章要讲的追踪（Trace）的数据基础——**追踪能力不是外挂上去的，而是协议的结构本身送出来的**。

**第三，性能与成本的归因。** 有了每次调用的 token 数与耗时，才能回答"这条链路的成本主要花在哪一步""哪个工具调用最慢"。没有这层数据，成本优化只能靠猜。

这里有一个可以推广的设计原则：**如果一类横切关注点（日志、追踪、指标、缓存、权限）需要在每个组件里重复实现，那它就应该被提升到协议层。** 回调正是把"横切关注点"从实现层提升到协议层的标准手法。

## 常见误区与排查

- **"配置直接放在输入里更方便"** → 症状：切换环境（开发/生产）时要改业务数据；或者配置项被当成提示变量拼进了模板。根因：缺少独立的配置通道。修法：凡是运行时参数，一律走配置注入通道，不进入输入输出结构。
- **"批量执行是并发的，所以写好顺序也没关系"** → 症状：结果与预期错位，日志里的先后顺序与代码顺序不符。根因：混淆了结果顺序与执行顺序。修法：只依赖结果顺序，不依赖完成顺序；需要顺序执行时显式降并发。
- **"加了流式就应该能实时看到结构化结果"** → 症状：想对每个分片做解析，结果总是解析失败。根因：流式分片是增量的，任何时刻都不是完整结构。修法：把校验与解析放在流结束后，或者在链路末端保留一个聚合步骤。
- **"同步和异步随便混，反正都能跑"** → 症状：偶发卡顿、超时、资源占用异常。根因：在一种上下文里调用了另一种执行路径。修法：项目内统一轨道，转换只在一处发生并标注。
- **"观测是运维的事，写代码时不用管"** → 症状：线上问题只能靠复现，而概率性系统复现不了。根因：把横切关注点留在了实现层。修法：把回调从第一天就接上，哪怕只是写进文件。

## 本章要点

- 适配爆炸的根本原因是缺少统一协议；协议的价值不是让代码变短，而是让组合成本从乘性降为线性。
- 统一协议必须包含四要素：输入输出契约、执行模式枚举、独立配置通道、生命周期钩子。缺任何一项，组合会在特定场景断裂。
- 四种执行模式的差异是实质性的：结果数量、到达方式、阻塞方式三个正交维度，共同决定了必须四种都存在。
- 流式与结构校验存在天然张力：任何依赖完整结构的判断都必须等流结束。
- 同步/异步双轨制是不可回避的代价，应对策略是统一轨道、单点转换、明确标注。
- 回调机制把可观测性从实现层提升到协议层，是追踪能力的数据基础。
- 可推广的原则：需要重复实现的横切关注点，应该被提升到协议层。

## 迁移视角：如果不用这个框架

把所有框架术语剥掉，这一章讲的是一件事：**为你的领域定义一套统一执行协议。**

这套做法在别处到处可见。数据库驱动有统一接口（所以换数据库不用重写业务逻辑）；HTTP 框架有中间件契约（所以日志、鉴权、限流可以横切）；构建系统有统一的"任务"概念（所以依赖图可以统一调度）。它们的共同结构都是本章的四要素：统一的输入输出形状、明确的能力枚举（同步/异步、流式/非流式）、独立的配置通道、生命周期钩子。

如果你自己设计一套执行协议，这一章给了两张检查表。第一张是四要素清单——过一遍，看有没有哪一格是空的。第二张是"这个能力会不会需要在每个组件里重复写"——凡是答案为"会"的，都应该提升到协议层。

还有一个容易被忽略的判断标准：**好的执行协议应该让你能对"执行"这个词做出确定的陈述。** "一次调用要么完整返回要么抛错"、"配置不参与数据流"、"所有执行都可被外部观察到"——这些是可以写进文档并被验证的。当协议做不到这些时，它的使用者就会各自发明一套补充约定，而补充约定是不统一的，问题就回来了。
