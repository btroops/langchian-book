# 第 19 章　部署与运行时形态

> 智能体的部署约束和普通 Web 服务不一样。它要处理的是长任务、可中断、可恢复的负载，而不是毫秒级的请求。

## 引子

一个智能体在开发环境跑得很好，部署到生产后遇到了一连串问题。

第一个是超时。负载均衡器的默认超时是 60 秒，而这个智能体处理复杂请求需要 3 分钟。于是大量请求在完成前被切断。

第二个是重复执行。用户在网络超时后点了重试，服务端于是又跑了一遍完整的流程——包括其中的两个写操作。

第三个是重启丢任务。滚动发布时，正在执行的流程随进程一起消失。用户看到的现象是"提交了但什么都没发生"。

第四个是成本失控。同一天出现了几笔异常高的账单，查出来是某个请求在循环里转了三十多轮。

这四个问题的共同点是：**它们都不是模型的问题，都是"把长时任务塞进请求-响应模型"造成的。** 传统 Web 服务的假设是"请求很快就结束"，而智能体的负载特征完全不同：单次请求可能持续很久、可能中途需要等待外部输入、可能产生副作用、成本随执行路径浮动。

这一章讲这些约束如何决定部署形态，以及三种可选形态各自的适用边界。

## 负载特征决定了架构

先把智能体负载的四个特征列清楚，因为它们直接推导出架构要求。

**特征一：长时。** 一次执行可能持续数秒到数天（含中断等待）。这打破了"请求期间完成一切"的假设。

**特征二：可中断。** 执行可能在任何同步点停下等待外部输入。这要求执行可以被安全地暂停和恢复，也要求"暂停"是一个可以被外部系统感知的状态。

**特征三：有副作用且需要幂等。** 执行中包含不可逆动作，且因为可能重试或恢复，这些动作必须能安全地重复。

**特征四：成本随路径浮动。** 同一个接口的两次调用成本可能相差十倍。这要求预算控制是执行时的能力，而不是事后的统计。

这四条推导出的架构要求是：**执行与请求解耦**（长任务不能绑在 HTTP 连接上）、**状态外置**（执行可以在任意实例上继续）、**副作用需幂等**（重复执行安全）、**预算需在线控制**（超标能中止）。

**"立即返回标识"这一步是分水岭。** 只要引入了它，接口语义就从"同步完成"变成了"提交任务"，客户端需要通过查询或通知获取结果。这个改动会影响前端设计、用户体验、以及错误处理方式——它不是一个纯技术改动，而是一次交互模式的变更。

## 三种部署形态

**形态一：进程内库。** 智能体作为应用代码的一部分运行在同一个进程里。适合短时任务、无需中断恢复的场景。

优点是简单：没有额外的服务、没有网络开销、调试路径短。缺点是**与进程生命周期绑定**（重启即丢失）、无法独立伸缩（模型调用的负载与 Web 请求的负载混在同一批实例上）、并且无法处理长时中断。

适用判断：任务在秒级完成、不需要人工介入、失败重跑成本可接受。

**形态二：独立服务。** 智能体作为独立服务部署，有自己的伸缩策略、自己的队列、自己的状态存储。

优点是**解耦**：模型调用的伸缩与 Web 层的伸缩独立；长任务可以有自己的处理模型；状态集中管理便于恢复。缺点是引入了服务间通信、部署复杂度、以及运维成本。

适用判断：存在长时任务、需要中断恢复、或者模型负载需要独立伸缩。

**形态三：托管运行时。** 把执行交给平台提供的运行时，平台负责调度、持久化、伸缩、以及提供人工介入的接口。

优点是**省掉了大量基础设施工作**：持久执行、检查点存储、中断恢复、可观测性都由平台提供。缺点是**与平台绑定**。这里的绑定是双向的：既包括部署方式的绑定，也包括**历史数据与执行语义的绑定**——第 13 章讲的检查点格式、会话标识约定都会沉淀在平台里，迁移需要数据转换与实践对齐。

适用判断：团队没有基础设施投入意愿、需求与平台能力高度重合、且能接受绑定。

| 形态 | 主要优势 | 主要代价 | 适用判断 |
|---|---|---|---|
| 进程内库 | 简单、无额外运维 | 与进程生命周期绑定、无法长时中断 | 秒级任务、无人工介入、可重跑 |
| 独立服务 | 解耦、可独立伸缩、状态集中 | 服务间通信、部署与运维复杂度 | 有长时任务、需中断恢复、需独立伸缩 |
| 托管运行时 | 免基础设施、能力开箱可用 | 平台绑定（含数据与语义） | 需求与平台能力重合、可接受绑定 |

一个常见的演进路径是：**从进程内库开始，遇到第一个"需要跨请求存活"的需求时升级到独立服务，当基础设施负担超过收益时再评估托管。** 这个顺序的好处是每一步的动因都清晰可查，而不是一开始就为想象中的需求买单。

## 队列、唤醒与超时

长时执行需要一套调度机制，它由四个部分组成。

**入队与出队。** 提交任务时先写入一条执行记录（包含状态与标识），然后入队。工作进程从队列取出任务执行。**入队与执行记录的写入必须是原子的**，否则会出现"入了队但没有记录"或"有记录但没入队"的不一致。

**暂停时释放资源。** 这是长时执行的关键设计。当执行需要等待外部输入时（第 14 章的中断），**不应该让一个工作进程一直挂着等待**——那会浪费资源并且限制并发容量。正确做法是：保存检查点、结束当前执行、释放进程，等外部输入到达后再重新入队继续。

**唤醒机制。** 外部输入到达后需要重新触发执行。实现方式有两种：**事件驱动**（输入到达时直接入队）和**轮询**（定期扫描待处理的中断）。事件驱动的延迟低但需要可靠的事件通道；轮询简单但延迟取决于扫描间隔。生产系统常用两者结合——事件驱动为主，轮询作为兜底（防止事件丢失）。

**超时分层。** 长时系统需要区分多种超时，混用会导致难以排查的问题。

| 超时类型 | 含义 | 处理方式 |
|---|---|---|
| 单次调用超时 | 一次模型或工具调用超时 | 重试或降级 |
| 单步执行超时 | 一个节点的总耗时超限 | 中止该节点并上报 |
| 整体执行超时 | 一次执行的墙钟时间超限 | 中止并通知用户 |
| 中断等待超时 | 等待外部输入的时长超限 | 过期处理（作废或升级） |
| 队列等待超时 | 任务在队列里未被处理的时长超限 | 告警扩容或降级优先级 |

**"中断等待超时"与"整体执行超时"必须区分开。** 一个任务可能整体允许三天完成，但其中某次人工审批只允许等待两小时。把两者混成一个超时会让你无法表达这种区别，从而在实现里到处打补丁。

## 成本与限流

智能体的成本控制有三个层面，必须都在线生效。

**层面一：单次执行的预算。** 在流程设计时就标注期望的调用次数、token 用量、耗时上限，执行过程中实时检查。超标即中止并上报。这是最基础的一道防线，也是唯一能防止"偶发极端路径导致账单暴涨"的手段。

**层面二：用户/租户的配额。** 限制单个用户或租户在给定时间窗口内的使用量。这既是成本控制，也是公平性保障（防止一个用户占满全部容量）。

**层面三：全局并发与速率限制。** 保护下游依赖（模型接口、内部系统）不被压垮。这一层通常与第 12 章讲的"并行约束"配合——图允许并行，但并发上限由外部依赖的能力决定。

**在线控制的必要性**需要特别说明。很多团队的做法是"先用着，看账单再优化"。这在低量时可行，但在高量时会造成严重问题：因为智能体的成本与路径长度正相关，而路径长度在某些输入下会异常增长。**如果没有在线检查，异常的路径会一直跑到结束才产生账单。** 所以预算检查必须能中断执行，而不是只做统计。

一个实用的设计是：**把预算作为状态的一部分。** 每消耗一次就写入状态（用累加型归约器，第 11 章），每一轮开始时检查是否超限。这样预算既被持久化（恢复后不会重置），又能被每一轮检查。这个设计与检查点机制天然契合。

## 灰度与回滚

提示、模型、工具集这些"行为定义"会频繁变更，而它们的变更没有编译器能验证，因此需要一套比代码发布更谨慎的流程。

**变更类型的风险等级不同。** 提示措辞调整风险中等（可能影响所有输出）；模型版本切换风险高（行为分布会整体偏移）；工具集变更风险高（可能影响调用准确率）；流程结构变更风险最高（可能影响在途任务的恢复）。

**灰度策略。** 常见的做法是按会话标识或用户标识分流，让一部分流量走新版本。**分流必须按会话粘性而不是请求粘性**——同一个会话的前后请求应该走同一个版本，否则上下文会不一致。

**在途任务的处理必须明确。** 部署新版本时，正在执行中的任务怎么办？三种选择：**排空**（等它们跑完再切换，最安全但发布慢）、**旧版本继续**（新任务走新版本，旧任务在旧版本上跑完，需要同时保留两个版本）、**迁移**（把在途任务迁移到新版本，最复杂，通常只在有明确迁移规则时使用）。**大多数情况应该选择排空或旧版本继续，并把这个选择明确写进发布流程。**

**回滚必须比发布更快。** 因为概率性问题不会在发布后立刻显现，往往是几小时后才从指标里看出来。所以版本切换要能快速回退，并且回退时要考虑"用新版本产生的历史数据，旧版本能不能处理"——这是版本兼容问题的另一个面。

**可观测性是灰度的前提。** 没有第 18 章的评估与监控，灰度就变成了"发布后祈祷"。分层的指标与回归集，是判断"是否需要回滚"的唯一依据。

## 常见误区与排查

- **"把长任务绑在 HTTP 请求上，超时调大就行"** → 症状：连接被中间层切断、网关超时、客户端重试导致重复执行。根因：没有把执行与请求解耦。修法：改为提交-查询模式，立即返回标识。
- **"等待人工审批时让进程挂着"** → 症状：并发容量被大量等待中的任务占满。根因：暂停没有释放资源。修法：保存检查点、结束执行、待输入到达后重新入队。
- **"所有超时统一设一个值"** → 症状：无法表达"整体允许很久但单步必须快"的需求，实现里到处打补丁。根因：超时没有分层。修法：按调用、单步、整体、等待、队列五层分别设定。
- **"成本控制放在月底看账单"** → 症状：偶发的极端路径造成账单暴涨。根因：没有在线预算检查。修法：把预算写入状态，每轮检查，超标即中止。
- **"部署新版本，在途任务自然会被处理"** → 症状：在途任务报错或行为错乱。根因：没定义在途任务的策略。修法：发布流程中明确选择排空或双版本并行。
- **"灰度按请求分流就行"** → 症状：同一会话前后行为不一致，用户体验割裂。根因：分流粒度错了。修法：按会话标识粘性分流。

## 本章要点

- 智能体负载的四个特征（长时、可中断、有副作用、成本浮动）推导出四项架构要求：执行与请求解耦、状态外置、副作用幂等、预算在线控制。
- "提交后立即返回标识"是交互模式的分水岭，它会连带影响前端设计与错误处理方式。
- 三种形态各有适用判断：进程内库（秒级、无介入、可重跑）、独立服务（长时、需恢复、需独立伸缩）、托管运行时（省基础设施、接受绑定）。绑定的不仅是部署方式，还包括历史数据与执行语义。
- 长时调度由四部分组成：原子性的入队与记录、暂停时释放资源、唤醒机制（事件驱动 + 轮询兜底）、分层超时。
- 超时必须分五层：单次调用、单步、整体执行、中断等待、队列等待。混用会导致无法表达真实需要。
- 成本控制三层面：单次执行预算、用户配额、全局并发速率限制。预算应写入状态以便持久化并在每轮检查。
- 灰度需要会话粘性分流、明确的在途任务策略（排空或双版本）、以及加速的回滚能力。可观测性是灰度的前提。

## 迁移视角：如果不用这个框架

这一章的内容几乎全部来自一个更古老的问题域：**长时运行任务的服务化**。定时任务系统、工作流引擎、消息队列消费者、批处理平台，都解决过同样的问题，也都有成熟的答案。

可以直接借用的经验有四条。

**第一条：提交-查询是长任务的通用交互模式。** 任何耗时超过几十秒的操作，都应该走这个模式，而不是让客户端死等一个连接。这个原则在网络编程早期就被确立了，与是否为智能体无关。

**第二条：等待不应占用资源。** 凡是"等待外部条件"的场景，都应该释放执行资源并在条件满足时重新触发。这个模式在事件驱动架构里是基础实践。

**第三条：超时必须按语义分层。** "多久算超时"这个问题的答案取决于超时的是什么东西。混在一起设一个值，是把本可以表达清楚的需求压成了一团模糊。

**第四条：成本控制在自动化系统里必须在线。** 因为自动化系统的成本与执行路径相关，而路径长短不可预知。任何按使用量计费的自动化（云计算、外部 API、按调用计费的第三方服务）都有这个特征，处理方式都是同一套：配额 + 在线检查 + 超标中止。

最后一条关于发布的经验值得强调：**行为定义（提示、模型、策略）需要比代码更谨慎的发布流程。** 因为代码的变更可以通过测试验证，而行为定义的变更只能通过观测验证。这不是"流程不够轻快"，而是这类系统的固有特征——**它的正确性无法在发布前被证明，只能在发布后被观察。** 承认这一点，并据此设计灰度与回滚能力，是这类系统能否稳定运行的现实条件。
