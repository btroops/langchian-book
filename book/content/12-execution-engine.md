# 第 12 章　执行引擎：超步模型与调度

> 并行节点加同步边界，是可复现性的来源。理解了这一章，你就能解释"为什么同一份检查点重放两次结果一样"。

## 引子

一个让人困惑的现象：同一个检查点重放两次，得到的结果完全一致；但如果把同一段逻辑单独跑两次（不经过重放），结果会不一样。

很多人会把这个现象归结为"框架做了某种缓存"。实际原因更朴素：**重放时被恢复的不只是数据，还有调度决策。** 引擎知道上一轮激活了哪些节点、边是怎么求值的、合并发生在什么时候。恢复后它按同样的顺序重做同样的决策，而节点是纯函数，所以结果一致。

反过来，如果不经过重放而是"重新跑一遍逻辑"，那么每一个依赖外部世界的环节（模型采样、接口返回、当前时间）都会给出新的值，路径随之分叉。

这个对比揭示了执行引擎的核心职责：**把"执行"变成一件可确定的、可重演的事。** 这一章要讲清它是怎么做到的，以及这个能力有哪些边界。

## 超步执行模型

这个模型有一个学术名字叫整体同步并行（BSP），它在大规模图计算里被验证过。它的核心取舍是：**用"每轮都要等最慢的节点"换取"每轮结束时的状态是完全确定的"。**

这个取舍非常关键。BSP 放弃了异步执行可能带来的效率，换来的是三个工程上极其宝贵的能力。

**能力一：状态在每个同步点都是自洽的。** 因为合并是统一发生的，不存在"状态处在中间态"的时刻。这让快照变得有意义——你可以在任何同步点保存状态，而且保存下来的是一份逻辑上完整的状态。

**能力二：并行结果是确定的。** 同轮内的节点互不可见，所以它们的执行顺序不影响结果（前提是归约器设计正确）。如果是异步执行，节点完成顺序会影响它能读到的状态，结果就不确定了。

**能力三：可复现的重放。** 由于调度决策（激活集、边求值）是确定的，只要节点是纯函数，整条执行路径就是确定的。

与之相对的异步模型（谁先完成谁先推进）在吞吐上更好，但会引入"同一份输入可能走出不同路径"的问题。对一个需要人工审批、需要审计、需要事后复盘的系统来说，这个代价通常不可接受。**所以这里的选择不是性能取向，而是可靠性取向。**

## 调度决策

"下一步执行谁"这件事在超步模型里分成三个环节。

**环节一：激活集的确定。** 一轮开始时，引擎知道哪些节点应该执行。这个集合来自上一轮结束时边的求值结果，或者来自开始节点的初始激活。**激活集是一个集合而不是一个序列**——同轮节点之间没有顺序，这是"并行"的准确含义。

**环节二：边在什么时刻求值。** 边的求值发生在一轮结束、状态合并完成之后。这个时机很重要：**条件边看到的是合并后的完整状态**，而不是某个节点的局部结果。所以条件边可以放心地依据状态里的任意字段做判断，包括本轮多个节点共同产出的内容。

**环节三：终止判定。** 终止在超步模型里会有几种表现，需要区分清楚。

**正常终止**是激活集为空——没有任何节点被激活，且存在已到达的出口。这是设计正确的流程结束的方式。

**异常终止**是达到某个约束上限（步数上限、成本上限、时间上限）。这不是流程设计好的结束，而是保护机制触发，它必须以明确的信号告知外部，否则用户会以为任务成功完成了。

**静默挂起**是一种危险的状态：激活集不为空却没有边界可以被激活。这通常是边定义不完整导致的（比如某个条件分支的两条路都没有覆盖所有情况），表现为流程"卡住不动"。这类问题在测试环境里如果只覆盖了正常路径就不容易被发现。

## 确定性从何而来

这是本章最有价值的分析。要能回答"为什么重放一致"，就要先知道有哪些东西会破坏确定性。

| 破坏源 | 表现 | 是否被检查点覆盖 |
|---|---|---|
| 模型采样 | 同一提示两次输出不同 | 重放时被覆盖（使用已记录的调用） |
| 外部接口返回 | 同一请求两次返回不同 | 重放时被覆盖（使用已记录的结果） |
| 当前时间 | 同一逻辑在不同时刻结果不同 | 不覆盖，需要显式冻结或作为状态保存 |
| 随机数 | 每次执行随机路径不同 | 通常是节点内部的私有逻辑，重放时被跳过 |
| 集合遍历顺序 | 字典/集合的遍历顺序可能不同 | 不覆盖，取决于语言实现 |
| 并发完成顺序 | 同轮节点完成顺序不同 | **被超步模型消除** |
| 节点内部状态 | 节点有自己的成员变量 | 不覆盖，属于反模式 |

这张表给出了一个极其实用的结论：**检查点的作用是"把已发生的外部交互变成可重放的数据"，而不是"消除随机性"。** 重放时不会再去调用模型，而是使用当时记录下来的调用结果。所以重放的一致性是"历史重演"，不是"重新计算得到相同答案"。

这也解释了另一个常见疑问：为什么不建议"重跑一遍来复现问题"？因为重跑会重新采样、重新调用接口、重新读取当前时间，路径大概率不同。**要复现，就要回放，不要重跑。**

由此可以推出几条设计约束。

**约束一：节点应该是纯函数。** 它读状态、做计算、返回增量。凡是与外部世界的交互，都应该通过可被记录的方式发生（模型调用、工具调用这些都在引擎的记录范围内）。节点自己偷偷调接口、读时钟、用随机数，会让重放失真。

**约束二：时间必须显式对待。** 如果逻辑依赖"现在"，那么"现在"应该作为一个状态字段在流程开始时确定下来，后续使用这个字段而不是重新读时钟。这样重放时时间就被冻结在历史值上。

**约束三：不要在节点之间依赖外部共享的可变状态。** 比如两个节点都写同一个内存缓存，或者读同一个全局配置。这类依赖不在引擎的视野内，会破坏重放。

## 与工作流引擎的对比

这套模型与成熟的工作流引擎（比如数据管道调度、通用工作流编排）有很强的相似性，也有本质差异。对比有助于看清哪些设计是从别处继承的、哪些是新的。

| 维度 | 通用工作流引擎 | 智能体执行引擎 |
|---|---|---|
| 任务粒度 | 相对固定的作业单元 | 单次模型调用或工具调用，粒度更细 |
| 图的形状 | 多为 DAG | 允许环，需显式终止控制 |
| 输出确定性 | 任务输出确定 | 任务输出概率性，需要契约校验 |
| 状态规模 | 状态较小，多为参数与元数据 | 状态含消息历史，规模大且增长快 |
| 数据依赖 | 显式参数传递为主 | 共享状态 + 增量合并 |
| 执行次数 | 一般一次 | 可能在同一节点反复执行（循环） |
| 成本模型 | 主要是一次性算力 | 每次调用都产生费用，需实时预算控制 |
| 暂停目的 | 等待依赖、等待资源 | 等待人类决策、等待外部条件 |
| 可复现性 | 靠版本与快照 | 靠检查点重放（因外部调用不可重算） |

**最大的不同在最后一行。** 工作流引擎的"重跑"通常是可行的，因为任务是确定性的——同样的输入会产生同样的输出。而智能体引擎不行：模型调用不可重算（会得到不同结果），并且如果重跑，副作用会被重复触发。所以**检查点在这里不是优化，而是可复现性的唯一实现方式**。

另一个重要不同是**成本是执行时产生的**。工作流的成本主要在部署资源上，而智能体的成本随执行路径实时增长。因此预算控制必须是执行引擎的内置能力，而不是外部的监控告警——等你收到告警，钱已经花掉了。

## 并发控制的现实约束

引擎提供了并行能力，但现实世界里并行的约束来自外部。这些约束必须在设计时就被处理，而不是等到限流报错。

**约束一：外部速率限制。** 模型的接口有每秒请求数与 token 速率的上限。同一轮并行激活十个节点会同时发起十个调用，直接打满限流。应对方式有三种：设置并发上限（牺牲并行度保稳定）、把调用排队（引入队列层）、按重要性分级（关键路径优先，其余退避）。选择依据是"这个并行是否真的必要"——很多时候并行只是因为"顺手"，并没有真实的延迟要求。

**约束二：共享资源。** 如果多个节点要写同一个外部系统，并行会带来竞态。典型场景是多个节点往同一张表插数据、往同一个文件追加、调用同一个有状态的服务。这类问题的标准解法是**把这部分操作串行化**——在图的结构上让它们分属不同超步，或者在上层加锁。

**约束三：幂等性。** 这是并发和恢复共同要求的性质。因为节点可能被重放（恢复时）、可能被重试（失败时），所以有副作用的操作必须能安全地重复执行。实现方式通常是"幂等键 + 外部系统去重"，或者"先查状态确认未执行，再执行，再记录已执行"。

注意最后一种方式的一个陷阱：**"查—执行—记录"这三步如果不在同一个事务里，依然是竞态的。** 正确的做法是把"已执行的记录"当作执行的一部分原子地写入，或者依赖外部系统自身的幂等能力（比如幂等键由外部服务去重）。第 13 章会展开这一点。

**约束四：并行带来的调试难度。** 并行执行的时间线不再是一条直线，日志会交错，问题难以重现。这是并行的隐性成本，它不该被忽略。实用的缓解办法是：并行度尽量小，节点尽量短，并保证每一步都有完整的状态快照可查。

## 常见误区与排查

- **"重跑一遍就能复现问题"** → 症状：本地怎么都复现不了线上问题。根因：重跑会重新采样、重新调用外部接口。修法：用检查点回放，而不是重跑。
- **"节点里读一下当前时间很方便"** → 症状：重放时结果与当时不一致，出现无法解释的差异。根因：时间不在引擎的记录范围内。修法：把时间作为状态字段在流程开始时确定。
- **"流程卡住不报错，说明只是慢"** → 症状：任务长时间无进展也无异常。根因：静默挂起——激活集非空但没有可达出口。修法：检查条件分支是否覆盖了所有情况；为分支设置兜底路径。
- **"并行越多越快"** → 症状：触发限流，整批任务一起失败。根因：忽略了外部速率约束。修法：设定并发上限，或改为队列排队。
- **"同一个外部表多个节点并行写没问题"** → 症状：偶发数据错乱或死锁。根因：共享资源竞态。修法：让这些操作分属不同超步，显式串行化。
- **"约束上限只在测试环境配得小，生产配得大"** → 症状：生产环境偶尔出现异常的长时间循环，账单激增。根因：约束上限脱离实际预算。修法：上限按成本预算设定，并在触发时显式上报。

## 本章要点

- 超步模型（BSP）的取舍是"每轮等最慢节点"换"每个同步点的状态确定性"，这是可靠性取向的选择。
- 同轮节点互不可见，边隐含了产生新超步的含义；一轮耗时由最慢节点决定。
- 调度分三环节：激活集的确定、边在合并后求值、终止判定。终止有正常、异常、静默挂起三种，后两种都必须显式上报。
- 检查点的作用是"把已发生的外部交互变成可重放的数据"，而不是消除随机性。所以复现要靠回放，不能靠重跑。
- 破坏确定性的来源中，并发完成顺序被超步模型消除；时间、随机、节点内部状态不被覆盖，需要显式设计。
- 与通用工作流引擎的最大差异在可复现性实现方式：智能体的模型调用不可重算，检查点是唯一手段；且成本是执行时实时产生的，预算控制必须内置。
- 并发的现实约束有四条：外部速率限制、共享资源竞态、幂等性要求、调试难度上升。

## 迁移视角：如果不用这个框架

这一章的三个概念可以独立于任何框架使用。

**第一个概念：同步边界是确定性的来源。** 任何并行系统都面临"如何让结果可预期"的问题。整体同步的答案是"在边界上对齐"，异步的答案是"让操作可交换"。前者实现简单、结果确定，代价是等待；后者吞吐高，代价是设计要求高。你在设计任何并行流程时都应该明确自己选了哪一条，而不是混着来。

**第二个概念：重放与重跑是两件不同的事。** 这个区分在分布式系统里早就存在了（事件溯源的回放、消息队列的重投递），但在智能体场景里它的重要性被放大，因为外部调用既昂贵又不可重算。**凡是有副作用和不确定外部调用的系统，都应当把"可回放"当作一等能力**：记录足够的信息，使得任何一次执行都能被精确重演。

**第三个概念：预算是运行时的一等公民。** 传统系统里资源成本与执行时间的关系是间接的，可以把成本控制放在外部（监控、限额）。智能体系统里成本与执行路径直接成正比，所以预算必须是执行引擎的内置能力，在每一步都能被检查、被中断。这个"把成本变成执行约束"的思路，在任何按使用量计费的自动化系统里都适用。

最后一条关于调试的经验值得带走：**并行系统的日志必须带超步标识和节点标识。** 因为时间线是交错的，按时间读日志会得到误导性的因果关系。按超步分组读，才能看出"这一轮发生了什么"。这是排查并行问题时最省力的一个习惯。
