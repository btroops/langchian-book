# 第 16 章　Schema 契约与 Pydantic 的角色

> Schema 是 Agent 系统里唯一能挡住不确定性的墙。它的价值不在定义数据形状，而在"非法数据无法通过"。

## 引子

一个订单处理智能体上线两周后，财务同事发现了一批金额异常的记录：本该是 1280 元的退款，实际执行成了 128000 元。

追查发现，模型返回的结构里那个金额字段是字符串 "1280.00"，而下游处理时做了一次隐式的类型转换与单位换算。看起来是转换逻辑写错了，但根本原因在更早的地方：**这个字段从来没有被声明过它的类型和单位。**

没有人说过它是数字还是字符串，也没有人说过它的单位是元还是分。模型按自己的理解给了字符串；下游按自己的理解做了换算。两者都"合理"，结果错误。

这类事故的特征很鲜明：**没有任何一个环节报错。** 类型不对时没有校验拦住，单位不明时没有断言检查，换算逻辑本身也没有异常。系统在每一处都"正常运行"，然后产生了一个错误的业务结果。

如果这个字段在系统边界上有一份明确的声明——类型是数值、单位是元、范围约束是什么——那么模型给字符串时就会被拦下，下游也不会去做猜测性的换算。这一章讲的就是这堵墙怎么建、建在哪里、以及建得不好会怎样。

## 三处 Schema

Agent 系统里有三个位置需要结构声明，它们的用途不同，设计标准也不同。

**位置一：模型输出的结构。** 声明你期望模型产出什么。这处的 Schema 有双重作用：对内是校验依据，对外（传给模型）是生成约束。它的设计要点是**贴合模型的理解能力**——字段名要自解释、描述要说清格式与单位、避免深层嵌套（嵌套越深，模型出错的概率越高）。

**位置二：工具参数的结构。** 声明工具接受什么。这处的 Schema 的关键要求是**参数必须无歧义**。日期用什么格式、金额带不带单位、枚举值有哪些合法取值——这些必须在描述里说清楚。因为工具的调用者不是人类工程师（可以看代码），而是模型（只能看描述）。**描述不清的工具参数是工具调用失败的首要原因。**

**位置三：流程状态的结构。** 声明状态里有哪些字段、各自什么类型、如何合并（第 11 章的归约器）。这处的 Schema 的作用是让状态可序列化、可合并、可解释。它的设计要点与前面两处不同：不需要贴合模型，只需要服务于系统的正确性与可维护性。

| 位置 | 主要消费者 | 设计重点 | 失败的表现 |
|---|---|---|---|
| 模型输出 | 模型 + 校验层 | 字段自解释、避免深嵌套 | 模型产出结构偏差，解析失败 |
| 工具参数 | 模型 | 格式与单位无歧义、枚举合法值明确 | 工具被错误调用或参数错误 |
| 流程状态 | 宿主程序 | 可序列化、归约语义明确 | 并发丢数据、恢复失败 |

一个值得坚持的约定是：**这三处 Schema 应该使用同一套类型系统。** 如果输出结构用一套声明方式、状态用另一套、工具参数用第三套，那么它们之间的转换就会靠手工代码，而手工代码是错误与不一致的温床。统一类型系统还有一个附带好处：模型输出的结构可以直接参与状态更新，不需要中间转换层。

## 校验即防线

这是本章的核心论点：**Schema 的真正价值是"拒绝"，不是"描述"。**

在确定性系统里，类型声明主要用于静态检查，让编译器帮你发现错误。在概率性系统里，编译期检查远远不够——因为输出的合法性取决于运行时模型的行为，而不是代码逻辑。所以 Schema 必须以**运行时校验**的形式存在，并且必须在**系统边界上**被执行。

"系统边界"这个概念需要具体化。它指的是**不确定性进入系统的地方**：

- 模型的输出进入系统的位置；
- 工具返回的结果进入系统的位置；
- 外部数据（检索内容、用户输入、第三方接口）进入系统的位置。

这三个位置之后的代码，都可以假设数据是合法的。这是这条防线最大的价值：**它把"不确定性"限制在一个可枚举的范围内。** 系统里绝大多数代码不必考虑"如果模型返回了一个意外结构怎么办"，因为那种情况在那三个位置已经被拦住了。

这个概念有一个很有用的推论：**如果某个校验不在边界上，它多半是浪费的。** 在系统内部反复校验已经校验过的数据，除了增加噪音之外没有收益。反过来说，**如果某个边界上没有校验，那里就是一个漏洞。**

除了"拒绝非法结构"，Schema 还能承担两类更有价值的约束。

**语义约束。** 不只是"这是一个整数"，而是"这是一个大于零的整数"、"这是一个在给定范围内的数值"、"这是一个符合特定格式的标识"。这类约束能拦住"格式合法但业务上无意义"的数据——比如金额为零、日期在未来、标识格式不符合规则。这类问题在下游往往表现为难以定位的逻辑异常。

**一致性约束。** 跨字段的约束，比如"如果类型是退款，则原订单号必填"。这类约束的复杂度更高，但价值也更大，因为它们拦住的正是"看起来完整但内部矛盾"的结构——这类结构最容易被忽略，最终产生无法解释的业务行为。

## 类型到提示的映射

Schema 不只是给程序看的，它还会被转换成给模型看的描述。这个映射的细节决定了模型能否稳定地满足约束。

映射的要素有五项：**字段名、类型、是否必填、描述、可选值范围。** 其中影响最大的是描述。

**字段名要自解释。** `amount` 比 `amt` 好，`refund_amount` 比 `value` 好。模型依赖名称推断语义，模糊的名称会引导它猜测，而猜测就是错误的开始。

**描述要写"是什么"和"格式要求"，不要写"用途"。** 有效的描述是"订单金额，单位：元，保留两位小数"；无效的描述是"用于计算退款金额的字段"——后者没有提供任何格式信息。

**单位与格式必须在描述里明确。** 这是引子里那个事故的直接原因。同样一个数值字段，如果不说单位，模型可能给 1280，也可能给 128000（分）。**凡是涉及单位的字段，描述里必须写明。**

**枚举值要列出全部合法取值。** 如果某个字段只能取三个值，就把这三个值写在描述里。如果依赖模型自己推断合法取值，它的选择空间会比实际需要的大得多。

**必填与可选的区分要谨慎。** 把所有字段都设为必填会导致模型编造内容来满足约束；全都设为可选会导致下游处理时到处判空。实用的做法是：**业务上必然存在的字段设为必填，其余设为可选，并在下游对可选字段的缺失有明确处理。**

## 校验失败的处理分支

校验失败是常态而不是异常。失败后怎么处理，有四个分支，必须提前设计好。

**分支一：重试。** 带上校验失败的**具体原因**让模型重新产出。这一步的关键是"具体原因"——只告诉模型"格式错误"几乎没有帮助，告诉它"字段 `amount` 期望是数值，实际是字符串，请只输出数值"才有帮助。**重试的有效性几乎完全取决于反馈的精确度。**

重试必须限次数（通常一到两次），因为模型的失败往往有系统性原因（比如描述不清），重复尝试不太可能自愈。

**分支二：修复。** 只做无歧义的还原（第 8 章的原则）：字符串 "1280" 还原成数值 1280 是无歧义的；但 "1280.00" 是元还是分是有歧义的，不能靠猜。**修复的边界是"能否在不做任何假设的情况下完成"。**

**分支三：降级。** 换一条更宽松的路径获取同样的数据。比如从"结构化输出保证"降级为"提示约束加宽松解析"，或者从"一次调用出完整结构"降级为"两次调用分步获取"（第 7 章）。降级的代价是可靠性或延迟，必须在可控范围内。

**分支四：上报。** 显式失败，交给上层决定。这是最后一道出口，也是必需的——**没有这个分支，失败就会被静默吸收**，变成默认值继续往下流。

四个分支的优先级通常是：先尝试重试（成本最低、成功率最高），失败后尝试无歧义修复，再失败后降级，最后上报。**但"上报"必须真实存在并且真的会被触发**，否则前三个分支就成了掩盖问题的手段。

## 反面案例：过严与过松

Schema 设计的两种失败都有清晰的症状。

**过严的症状：模型永远无法满足约束。**

表现为重试次数恒定、失败率恒定偏高、成本因重试而飙升。常见原因有三种：约束在业务上不合理（要求模型输出它不可能知道的信息）；字段太多导致一次产出难度过高；跨字段一致性约束相互冲突（要求同时满足两个互斥的条件）。

诊断方法很直接：**把模型的实际输出与约束逐项对比，看哪一项永远不满足。** 如果某一项从来没人满足过，那它不是"模型能力不足"，而是约束本身有问题。

**过松的症状：下游崩溃或静默出错。**

表现为系统里有大量防御性判空代码；偶尔出现难以定位的逻辑异常；或者（更糟）不报错但结果不对。常见原因是把所有字段都设为可选、把类型都设为宽泛类型（比如"任意对象"）、以及缺少取值范围的约束。

诊断方法同样直接：**看一下系统内部有多少处代码在处理"字段可能不存在"的情况。** 如果到处都是，说明 Schema 太松，把不确定性泄漏到了系统内部。

取中的原则可以概括成一句话：**约束应该表达"业务上真正必需的东西"，而不是"我们能想到的所有检查"。** 每一条约束都应该能回答"不加它会怎样"——如果回答不上来，这条约束就是噪音。

## 常见误区与排查

- **"字段单位很明显，不用写在描述里"** → 症状：金额、时长、比率类字段偶发量级错误。根因：单位依赖了隐式约定。修法：所有带单位的字段在描述里写明单位与格式。
- **"校验失败就重试，最多重试五次"** → 症状：成本飙升，失败率没改善。根因：失败有系统性原因，重试无法自愈。修法：限次数，并在重试时提供精确的失败原因；连续失败应视为约束设计问题。
- **"为了灵活，所有字段都设为可选"** → 症状：内部代码到处判空，偶发逻辑异常。根因：不确定性泄漏进了系统内部。修法：业务必然存在的字段设为必填。
- **"内部也要处处校验，双重保险"** → 症状：代码冗长，边界校验的缺失被内部检查掩盖。根因：校验没有集中在系统边界。修法：只在三个边界做严格校验，内部依赖契约。
- **"类型不符时自动转换一下就好"** → 症状：静默产生错误数据。根因：自动转换在没有单位与语义信息时引入了猜测。修法：只做无歧义转换，有歧义时走重试或上报。
- **"三处 Schema 各写一套更方便"** → 症状：转换代码增多，字段含义在不同地方不一致。根因：缺少统一类型系统。修法：统一声明方式，减少手写转换。

## 本章要点

- Schema 的价值在"拒绝"而非"描述"：在概率性系统里，编译期检查不够，必须有运行时校验。
- 三处 Schema：模型输出（贴合模型理解）、工具参数（无歧义）、流程状态（可序列化、可合并）。应使用统一类型系统。
- 校验必须在**系统边界**上执行：模型输出进入处、工具结果进入处、外部数据进入处。边界之后可假设数据合法。
- 不在边界上的校验多半是浪费；边界上没有校验的地方就是漏洞。
- 类型到提示的映射中，字段名自解释、描述写明格式与单位、枚举列出合法值，这三项影响最大。
- 校验失败的四个分支：重试（需精确原因、需限次）、修复（仅无歧义还原）、降级（换更宽松路径）、上报（必须真实存在）。
- 过严的症状是重试恒定失败，过松的症状是防御代码遍地。约束应表达业务必需项，每条都要能回答"不加会怎样"。

## 迁移视角：如果不用这个框架

"在边界上校验"是一条与框架无关的架构原则。任何系统都有"可信区"与"不可信区"的边界：用户输入、第三方接口、文件读取、消息消费。成熟系统的做法都是同一套：**在边界上做严格校验，把进入可信区的数据变成"有保证的数据"，此后内部代码不再做防御性检查。**

LLM 应用的新增之处在于**多了一个边界：模型输出。** 而且这个边界比传统边界更不稳定——第三方接口的行为至少在版本内是固定的，模型输出则每次都可能有细微差异。所以这一层的校验要求更高，还需要配套反馈机制（把失败原因回传给模型）。

另外两条结论也值得带到别处。

**第一条：类型系统是减少转换代码的工具。** 同一套数据在系统里流动时，如果每个环节都有自己的表示方式，中间就需要转换代码，而转换代码是 bug 的富集区。统一表示能消除整类问题。这个道理在前后端接口设计、数据管道、跨服务通信里都成立。

**第二条："不加会怎样"是一个普适的检查标准。** 无论是 Schema 约束、代码抽象、还是监控指标，都应该能回答这个问题。答不上来的东西，通常是在消耗维护成本而没提供价值。

最后一条关于沟通的经验：**约束的表达方式决定了它的可满足性。** 你对模型（或对同事、对下游系统）提出的要求，如果缺少格式与单位信息，对方只能靠猜。要求越精确，满足率越高——这不是"对方能力问题"，这是表达问题。这个道理在跨团队接口设计里早就被验证过无数次了。
