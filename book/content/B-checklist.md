# 附录 B　原理速查与自检清单

> 三个工具：一句话版的全书结论、可拿去评审的架构自检清单、以及故障到根因的排查路径表。用法见文末。

## 一、各章核心结论速查

每章压成一句话。遇到困惑时先在这里对一下，多数问题能直接定位到章节。

| 章 | 一句话结论 |
|---|---|
| 1 | 框架是被问题逼出来的：编排成本、循环控制、状态持久化、执行可观测依次逼出四层抽象 |
| 2 | 四个约束（窗口有限、无状态、概率性、副作用不可逆）推导出四件必需品：上下文装配器、外部状态存储、校验层、中断与预算 |
| 3 | 抽象只封装"变化"，不封装"选择"；判据是可组合、可替换、可观测 |
| 4 | 生态每一层都能追溯到一个具体失败；核心能力从组件层迁到运行时层的根因是职责错配 |
| 5 | 统一协议的要素缺一不可；横切关注点必须提升到协议层 |
| 6 | 声明式的价值是结构被保留；链路能否流式取决于有没有"必须等完整输入"的组件 |
| 7 | 适配层要抹平的是能力差异；工具调用协议的核心价值是意图与执行分离 |
| 8 | 提示模板是纯函数，解析器是三层防线：宽松抽取、严格校验、修复与升级 |
| 9 | RAG 的失效点几乎全在检索；检索层与生成层必须分开评估 |
| 10 | 循环 + 状态 + 终止条件 = 智能体；一旦允许环，终止性必须由显式控制承担 |
| 11 | 读全量、写增量；归约器决定并发安全，用错归约器的三种症状是数据变少、无限增长、数值偏高 |
| 12 | 同步边界是确定性的来源；复现要靠回放不能靠重跑 |
| 13 | 节点级原子性不存在；幂等键必须由产生副作用的一侧去重 |
| 14 | 中断是跨进程跨时间的退出与重入；恢复请求是一个高风险的写操作 |
| 15 | 多智能体是组织设计问题；只有"上下文隔离"与"工具集隔离"能带来收益时才拆 |
| 16 | Schema 的价值在"拒绝"；校验必须集中在三个系统边界上 |
| 17 | 协议化把 M×N 变成 M+N；工具失败是数据不是控制流；外部内容是指令的危险源 |
| 18 | 观测是发现问题的唯一途径；未校准的自动评分比没有评分更危险 |
| 19 | 负载的四个特征推导出四项架构要求；行为定义需要比代码更谨慎的发布流程 |
| 20 | 四种循环模式是基础结构；循环质量取决于失败能否被快速识别并终止 |
| 21 | 上下文工程的核心是判断"这条信息该放哪一层"，而不是"怎么塞得更多" |
| 22 | 五个必答设计题含糊即返工；三个陷阱：运行时当组件、观测留最后、假设模型会听话 |
| 23 | 主要工作不是让模型做对，而是让错误无法静默地传播 |

## 二、架构自检清单

三十条，按模块分组。每条都以问句形式给出，**答不上来或答得含糊的项，就是风险项**。

### 状态（4 条）

1. 状态里每个字段的**归约语义**是否明确？是否存在多个节点在同一个超步里写同一字段的情况？
2. 状态里是否含有不可序列化的对象（连接、句柄、客户端、闭包）？
3. 只看状态的内容，一个不了解系统的人能否说出"任务做到哪了、接下来要做什么"？
4. 累积型字段（列表、计数器）是否设了**上限与淘汰规则**？

### 控制流（5 条）

5. 是否显式定义了"目标达成"的终止判据，并且不单纯依赖模型的判断？
6. 是否存在"无法完成"这个**合法出口**？（缺它会让无解任务一直消耗预算）
7. 四类预算（步数、工具调用数、token、时长）是否都在线生效并能中止执行？
8. 是否有进展检测？能否识别"连续两轮没有新信息"这种情况？
9. 每个条件分支是否都有兜底路径？（缺它会造成静默挂起）

### 契约（4 条）

10. 模型输出、工具参数、流程状态三处 Schema 是否使用统一类型系统、是否都在系统边界处强制校验？
11. 所有涉及单位的字段，描述里是否写明了单位与格式？
12. 校验失败后是否存在真实的"上报"分支？还是会被默认值静默吸收？
13. 重试是否限定了次数，并在重试时传递了**精确的失败原因**？

### 工具与协议（4 条）

14. 工具失败是否以**结构化返回值**表达，而不是抛异常？
15. 工具集的大小与可区分度是否被审查过？（功能重叠的工具会推高误选率）
16. 工具返回的内容是否做了裁剪或结构化提取？是否可能单次调用吃光预算？
17. 工具返回的内容在装配进提示时，是否有明确的"这是外部内容"边界标记？

### 持久化与副作用（5 条）

18. 检查点保存的是否包含**外部交互记录**（模型调用与工具调用的输入输出）？只有状态是不够的。
19. 会话标识的粒度是否与业务上"一次连续交互"的定义一致？
20. 所有有副作用的调用是否都携带**幂等键**，且由产生副作用的一侧负责去重？
21. 流程结构变更时，在途任务的处理策略是否明确？（排空 / 双版本 / 迁移 / 作废）
22. 副作用调用是否收口在少数几个位置？（散落各处时，幂等正确性无法审查）

### 中断与人在回路（4 条）

23. 中断信息是否包含**待决问题的精确描述**，而不只是"停在这里"？
24. 恢复接口是否做了权限、时效、幂等、版本四项校验？
25. 中断是否设了有效期与过期处理？（否则会积累僵尸任务）
26. 是否存在"旧值还是新值"的明确策略来处理中断期间的外部数据变化？

### 观测与评估（4 条）

27. 六项关键埋点（模型调用输入输出、token 与耗时、工具调用、状态变化、控制流决策、会话与业务标识）缺了哪几项？
28. 线上出问题时，能否**在不改代码的情况下**拿到完整执行轨迹？
29. 是否支持**回放**（输入输出完整、顺序结构明确、执行可注入）？
30. 是否有分层指标（单步 / 轨迹 / 端到端）与人工校准过的评分标准？

## 三、常见故障 → 根因 → 排查路径

### 输出质量类

| 故障现象 | 可能根因 | 排查路径 |
|---|---|---|
| 回答流畅但内容错误 | 检索命中了"相似但不相关"的内容 / 无依据时未设计兜底行为 | 看轨迹里的检索结果与提示装配；检查是否要求引用依据 |
| 引用了不存在的依据 | 未要求标注引用 / 检索内容未带来源标识 | 检查提示是否要求引用，检查装配时是否带了来源 |
| 增加上下文后质量下降 | 注意力稀释超过信息效应 | 分类设上限；先做减法，看减少后是否变好 |
| 模型忽略明确给出的信息 | 该信息位于上下文中段 / 被其他内容淹没 | 检查该信息在提示中的位置；考虑移到首尾 |
| 换模型后行为整体偏移 | 采样参数与停止条件的语义差异（不可抹平的适配项） | 逐项对比两家供应商的参数含义；检查停止条件 |
| 回答中使用了自己的旧知识 | 未明确指示"仅依据给定资料" / 未定义无依据时的行为 | 检查系统指令是否包含这条约束 |

### 执行与控制类

| 故障现象 | 可能根因 | 排查路径 |
|---|---|---|
| 任务长时间不结束 | 缺少进展检测 / 终止判据不完整 | 看轨迹的轮间差异；检查是否有"连续两轮无新信息"的检测 |
| 任务卡住但无报错 | 静默挂起：激活集非空但无可达出口 | 检查条件分支是否覆盖所有情况；看检查点里下一轮激活集 |
| 过早收敛、任务未完成就结束 | 终止判据过于宽松 / 模型被允许自行宣告完成 | 检查终止条件；增加对"完成"的外部校验 |
| 同一工具被反复调用 | 工具可区分度低 / 失败信息不够具体 | 审查工具描述；检查失败返回是否包含修正建议 |
| 重试后成本上升但质量不变 | 重试的是结构性问题 / 未检测轮间是否改善 | 检查失败原因是否是系统性的；加"轮间提升"检查 |
| 触发限流后整批失败 | 并行度超出外部速率限制（第 12 章约束一） | 检查并发上限配置；改为队列或分级退避 |

### 数据一致性类

| 故障现象 | 可能根因 | 排查路径 |
|---|---|---|
| 并发执行后数据变少 | 归约器用了"覆盖"而实际需要"追加" | 逐字段检查归约语义与写入模式是否匹配 |
| 状态随轮数无限增长 | 累积字段缺去重或上限 | 检查列表型字段的追加规则 |
| 数值统计偏高 | "求和"用在了增量含全量的场景 | 检查计数类字段的语义是增量还是全量 |
| 恢复后出现重复下单/重复通知 | 副作用未做幂等，或节点内动作不具备原子性 | 检查副作用调用是否带幂等键；检查是否收口 |
| 启用持久化后报错 | 状态里含有不可序列化对象 | 检查状态字段类型；把资源移出状态 |
| 恢复后结果与崩溃前不一致 | 缺少外部交互记录，导致重放变成重算 | 检查检查点是否保存了模型与工具调用的输入输出 |

### 中断与运维类

| 故障现象 | 可能根因 | 排查路径 |
|---|---|---|
| 恢复后使用了过期数据 | 缺少"旧值还是新值"的显式策略 | 检查中断信息与恢复逻辑的价值取向 |
| 恢复方不知道该传什么参数 | 中断信息缺少待决问题的精确描述 | 检查中断构造的内容 |
| 同一中断被处理两次 | 恢复接口缺少幂等校验 | 检查恢复是否标记了"已解决" |
| 大量待办堆积无人处理 | 缺少通知补偿与升级路径 / 无有效期 | 检查通知机制与超时处理 |
| 发布后所有在途任务失败 | 未定义在途任务策略 | 检查发布流程是否包含排空或双版本方案 |
| 灰度后用户体验割裂 | 分流按请求而非按会话粘性 | 检查分流粒度 |

### 观测类

| 故障现象 | 可能根因 | 排查路径 |
|---|---|---|
| 线上问题无法复现也无法定位 | 观测数据不足（缺少完整输入输出） | 检查六项埋点覆盖情况 |
| 指标下降但不知原因 | 只有端到端指标，缺少分层指标 | 补齐单步与轨迹层指标 |
| 指标在改善但业务体感没变 | 自动评分未校准，偏离了要衡量的东西 | 抽样人工核对，处理评委偏差 |
| 改动效果无法判断 | 缺少固定的回归集 | 从线上失败案例建立用例集 |
| 观测成本成为显著开支 | 缺少分层保留与采样策略 | 改为失败全留、成功采样 |

## 四、评审会提问清单

在评审他人（或自己的）设计方案时，按顺序问这八个问题。**它们覆盖了返工成本最高的区域，且每个问题都有明确的"含糊"信号。**

1. **状态里有哪些字段？每个字段的合并语义是什么？** — 含糊信号：答"就是一些上下文"。
2. **流程在什么条件下会停止？如果任务根本做不成，会怎么结束？** — 含糊信号：答"模型会知道什么时候结束"。
3. **如果进程在第三步崩溃，恢复后会发生什么？** — 含糊信号：答"重新跑一遍"。
4. **系统里有哪些不可逆操作？它们如何避免重复执行？** — 含糊信号：答"不会被重复执行"。
5. **线上出了这个问题，你需要多久能定位到原因？靠什么数据？** — 含糊信号：答"加日志看看"。
6. **如果一个请求的成本是平均值的十倍，你会怎么发现并阻止它？** — 含糊信号：答"月底看账单"。
7. **这次改动如果效果变差，怎么判断？多快能回滚？** — 含糊信号：答"看用户反馈"。
8. **系统里有哪些"模型应该会……"的假设？它们被什么检查覆盖？** — 含糊信号：列不出来，或答"其实挺可靠的"。

**这八个问题的共同特点是：它们问的都是"出错时怎么办"，而不是"正常时怎么做"。** 因为正常路径几乎总能跑通，系统的可靠性由异常路径的处理质量决定。一个设计方案对异常路径的回答质量，基本就决定了它上线后的稳定程度。

## 结语

这份附录里的三张表——速查表、自检清单、故障排查表——都是同一批原理的不同投影。速查表回答"这个道理是什么"，自检清单回答"我有没有做到"，排查表回答"出了事怎么找"。

如果只带走一件东西，建议是**第二节那三十条自检清单**。它可以直接用在任何一个智能体系统的评审上，无论它用的是哪个框架、哪种语言。而且随着你经验增长，你会发现这三十条几乎不需要修改——需要改的只是你对每条的理解深度。

**原理的价值不在于它告诉你答案，而在于它告诉你该问什么问题。** 这一页上的问题，就是这本书想留下的东西。
