# 第 7 章　模型与消息：LLM 适配层的原理

> 适配层要抹平的不是 API 差异，而是能力差异。前者是工程活，后者是设计难题。

## 引子

"支持一百多个模型供应商"这句话听起来很有说服力，但它掩盖了一个问题：这些模型的能力并不一致。

有的模型原生支持工具调用，有的需要靠提示词诱导它输出特定格式；有的支持多模态输入，有的只接受纯文本；有的流式分片是逐 token 的，有的按语义块返回；有的在同一个响应里既给推理过程又给最终答案，有的把两者混在一起。当你的系统需要"换一个模型试试"时，真正让你痛苦的从来不是改一个模型名，而是**那些原本依赖的能力在新模型上不存在，或者语义不一样**。

所以这一章讲两件事：统一的消息模型如何定义"模型交互"这件事；以及适配层在面对能力差异时，哪些差异可以抹平、哪些注定泄漏。

## 消息角色模型

把"和模型的交互"抽象成一条**有序的消息列表**，是这个领域最重要的一个建模决定。它把散乱的字符串拼接变成了一种结构化数据。

消息列表里有四种角色，每一种都有自己的语义约束。

**系统消息（System）**定义模型的身份、约束和行为准则。它的特点是**优先级最高但强度不绝对**。说它优先级高，是因为它在语义上覆盖其他所有指令；说它强度不绝对，是因为当用户输入与系统约束冲突时，模型的行为并不总是可靠地遵守系统约束——尤其是当用户输入里包含精心构造的越权指令时。因此**系统消息是行为指引，不是安全边界**。真正的安全边界必须在宿主侧实现（权限校验、动作白名单、输出过滤），不能寄希望于提示。

**人类消息（Human）**代表外部输入。它有两个容易被低估的工程含义：一是它**不完全可信**，用户输入可能包含试图改变模型行为的指令；二是它**体量不可控**，用户可能粘贴一整篇文档进来，直接吃掉上下文预算。因此人类消息在进入消息列表前，通常需要经过裁剪或长度检查。

**模型消息（AI）**代表模型的产出。它不只是文本，还可能携带工具调用意图、推理过程、引用信息。把"模型的产出"建模成结构化消息而不仅仅是字符串，是与工具调用能力配套的必要设计——因为工具调用意图必须与文本内容分开表达，宿主机才能区分"这是要说给人听的"和"这是要执行的"。

**工具消息（Tool）**代表工具执行的结果。它有两条硬约束，也是实践中最容易踩的坑。

**约束一：必须紧跟对应的调用意图。** 消息序列的合法性要求"调用意图"和"执行结果"成对出现，顺序不能乱。如果工具消息出现在没有对应调用意图的位置，或者一个调用意图的结果缺失，消息序列在结构上就是非法的。

**约束二：必须携带匹配标识。** 当模型在一次响应里提出多个调用意图时，结果必须能一一对应回去。如果对应关系错位，模型会把 A 工具的结果当成 B 的，产生看似合理但完全错误的推理。

理解这四种角色的约束之后，很多"消息序列非法"的报错就变得可解释了：它们几乎都源于三种情况——角色顺序不对、调用与结果不成对、匹配标识丢失。

## 适配层必须处理的差异

统一接口的意义在于让调用方不必知道具体供应商。但差异是客观存在的，必须分类处理。

| 差异维度 | 具体表现 | 能否抹平 |
|---|---|---|
| 消息结构 | 内容块的组织方式、多模态表达方式不同 | 可抹平（转换为统一内容块） |
| 工具调用格式 | 调用意图的字段名与嵌套层级不同 | 可抹平（转换为统一的意图结构） |
| 流式分片粒度 | 逐 token、按语义块、按事件 | 部分可抹平（需容忍粒度差异） |
| 推理内容 | 有的单独返回，有的混在正文里 | 部分可抹平（无法分离时只能标记为"不可分离"） |
| 停止条件 | 停止序列、最大长度、工具触发停止的语义不同 | 难以完全抹平 |
| 计数与计费 | token 计算方式、缓存命中的计价规则不同 | 不可抹平（只能如实传递） |
| 采样参数 | 同名参数不同供应商含义不同 | 不可抹平（只能保留最低公分母 + 原样透传） |

这张表最重要的信息是下面那三行。**"难以抹平"和"不可抹平"的项，就是适配层必然泄漏的地方。** 认清这一点有实际价值：当你发现换个模型后行为变了，先看这三行——采样参数的含义差异、停止条件的行为差异、计费的差异，都能解释大量"换了模型结果就不一样"的现象。

一个成熟适配层的设计原则是：**把可抹平的差异彻底抹平，把不可抹平的差异显式暴露。** 后者不是失败，硬把不可抹平的东西假装统一才是失败——它会让使用者以为换了模型只是换个名字，然后在某天撞上无法解释的行为变化。

## 工具调用协议的本质

这是本章的核心机制，也是整个智能体能力的地基。

工具调用的本质是一套**三段式协议**：

**第一段：模型输出结构化意图。** 模型不做实际执行，它只输出一个结构化的描述——要调用哪个工具、参数是什么。这一步的关键在于**输出的结构受模型供应商的原生支持约束**，而不是靠后处理解析。这就把"模型决定做什么"变成了一个可靠的结构化输出问题。

**第二段：宿主执行。** 真正执行的是宿主程序。工具的实现、权限、超时、重试、日志全在宿主侧。这一步把"做什么"和"能不能做"分开了——模型提出的意图只是意图，宿主有绝对的否决权。

**第三段：结果回灌。** 执行结果被包装成工具消息，回到消息列表，模型基于它继续推理。这一步是循环的接续点：模型看到结果，决定是再调一个工具，还是给出最终回答。

**为什么这套协议优于"让模型输出 JSON 再解析"？** 三个理由。

第一，**结构由模型服务保证，而不是由提示词保证。** 提示词约束是"请求"，模型可能不遵守；原生工具调用是模型服务端参与解码的结构约束，可靠性高一个量级。

第二，**意图与执行分离。** 这给了宿主一个天然的插入点：在执行前做校验、审批、去重、限额。第 14 章的人在回路机制就挂在这条缝上。

第三，**结果是结构化的。** 结果以结构化形式回灌，模型对它的理解更稳定；而如果结果是拼进提示词的一段文本，模型需要猜测它的边界和含义。

一个反向的推论同样重要：**工具描述本身是提示词的一部分。** 工具的名称、说明、参数描述，都会进入模型的上下文并影响它的选择。所以"工具设计"是提示工程的一种形式——工具的命名、描述的精确度、参数的可区分度，直接决定模型的调用准确率。工具数量越多，可区分度越重要：给模型二十个功能相近的工具，出错率会显著高于给它五个清晰区分的工具。

## 结构化输出：三条技术路线

让模型产出程序可用的数据，有三种路线，可靠性依次递增，适用范围依次收窄。

**路线一：提示约束。** 在提示里说明格式要求，然后解析输出。优点是通用，任何模型都能用；缺点是可靠性最低，格式偏差是常态，必须配套解析容错（第 8 章）。

**路线二：工具调用式借用。** 定义一个"提交结果"的工具，把结果结构定义成这个工具的参数结构，让模型通过"调用工具"来提交答案。优点是复用了工具调用那条可靠的结构化通道；缺点是把"产出结果"包装成了一次"工具调用"，在语义上有点绕，并且在需要模型一边调用真实工具一边产出结构化结果时，可能产生干扰。

**路线三：受限解码。** 在模型生成时施加语法约束，只允许生成符合结构的 token 序列。这是可靠性最高的方式，因为它从生成层面排除了非法结构；缺点是依赖模型服务支持，且强约束有时会影响生成质量（模型被迫在结构上"想得太早"，推理质量下降）。

| 路线 | 可靠性 | 通用性 | 主要代价 |
|---|---|---|---|
| 提示约束 | 低 | 最高 | 必须配套容错解析，失败要重试 |
| 工具调用式借用 | 中高 | 高 | 语义绕路；与真实工具调用可能互相干扰 |
| 受限解码 | 最高 | 依赖服务支持 | 可能损伤推理质量；能力受供应商约束 |

实践中常见的组合是：**优先用受限解码或工具调用路线拿到结构保证，同时保留提示约束作为降级路径。** 这三条路线之间的切换能力，就是第 8 章讲的"降级输出"。

## 能力降级策略

当目标模型不支持所需能力时，可选策略有四种，各有明确的适用边界。

**策略一：提示模拟。** 用提示词诱导模型模仿缺失的能力（比如让它按格式输出"我要调用某某工具"）。代价是可靠性下降，需要一个更健壮的解析层。适合原型与非关键路径。

**策略二：拆成两步。** 把一次需要复合能力的调用拆成两次简单调用（先出文本，再用一次调用把它转成结构）。代价是延迟与成本翻倍，但可靠性可控。这是最常用的生产级降级方案。

**策略三：换供应商。** 把需要该能力的那一段单独路由到支持它的模型。代价是引入了多供应商复杂度，以及跨模型的一致性问题。

**策略四：显式拒绝。** 直接告知该能力不可用，不静默降级。这在关键能力上往往是最负责任的选择——静默降级会产出看起来正常但质量下降的结果，这正是第 2 章说的静默错误。

判断标准可以简化成一句话：**如果降级后的结果与正常结果的差异，用户能感知并且可接受，就降级；如果不能，就拒绝。** 不要用静默降级来掩盖能力缺失。

## 常见误区与排查

- **"把重要约束写在系统消息里就安全了"** → 症状：用户通过特定措辞绕过了约束。根因：把行为指引当成安全边界。修法：所有安全判定放在宿主侧，提示只负责引导。
- **"工具消息和调用意图的顺序不重要"** → 症状：消息序列非法的报错，或者模型把结果张冠李戴。根因：忽略了"成对且有序"的硬约束。修法：把消息序列的构造集中在一处，不要在多处手工拼接。
- **"换个模型只是改个名字"** → 症状：换模型后输出风格、长度、工具调用率都变了，甚至出现无法复现的错误。根因：忽略了采样参数与停止条件的语义差异。修法：把不可抹平的差异显式暴露，换模型时逐项检查。
- **"工具写得多，模型能力就强"** → 症状：模型在工具间选错，或者反复试错。根因：可区分度下降。修法：精简工具集，让功能重叠的工具合并或明确分工。
- **"模型说它调用了工具，就应该已经调用了"** → 症状：模型给出"已完成"的答复，但外部系统没有任何动作。根因：混淆了"输出调用意图"和"实际执行"。修法：永远由宿主执行并把真实结果回灌，不要让模型自行宣告执行结果。
- **"结构化输出失败就重试到成功"** → 症状：成本飙升，延迟不可控。根因：没有为重试设定上限和降级路径。修法：设定重试次数，超限后走降级路线或显式失败。

## 本章要点

- 把模型交互建模为有序消息列表，是这一层最重要的设计决定；四种角色各有硬约束。
- 系统消息是行为指引而非安全边界，安全判定必须在宿主侧。
- 工具消息必须与调用意图成对有序、携带匹配标识；消息序列的构造应该集中在一处。
- 适配层的真正难点是能力差异而非 API 差异；可抹平的彻底抹平，不可抹平的显式暴露。
- 工具调用的三段式协议（输出意图 → 宿主执行 → 结果回灌）的价值在于**意图与执行分离**，这是所有控制机制的插入点。
- 工具的描述与命名是提示工程的一部分，可区分度比数量重要。
- 结构化输出三条路线可靠性与通用性成反比；生产实践是"拿结构保证 + 保留降级路径"。
- 能力降级要遵循一条判断：差异用户可感知且可接受才降级，否则显式拒绝。

## 迁移视角：如果不用这个框架

这一章的内容几乎可以直接搬到你自研的任何系统里，因为消息模型和工具调用协议是**模型与宿主之间的接口约定**，与框架无关。

三条最有迁移价值的结论。

**第一条：把"意图"和"执行"分开建模。** 这是整个章节里结构最漂亮的一个设计。它带来的是控制权：因为模型只输出意图，宿主就有了校验、审批、去重、限额、记录的全部机会。这个模式在别处也成立——表单提交与后端校验、SQL 生成与执行前审查、配置声明与应用，都是同一个结构。**凡是"生成者与执行者分离"的地方，就存在一个可以插入控制的缝。**

**第二条：区分"请求"和"保证"。** 提示词是请求，结构化通道是保证。设计系统时应该明确标注每一处依赖的是哪一种。凡是关键路径依赖"请求"的地方，就是脆弱点，需要补充校验或改造为"保证"。

**第三条：适配层的诚实原则。** 统一接口最大的风险不是漏掉了某个供应商，而是伪装了不存在的统一性。把不可抹平的差异显式列出来，比一个看起来很干净的统一接口更有价值——因为前者让你在换实现时知道该检查什么，后者让你以为不用检查。

最后一条经验关于工具设计：**工具集是一份给模型看的 API 文档，它的使用者是模型而不是人。** 所以设计标准不是"人类工程师看着舒服"，而是"模型能否在给定的描述下稳定地做出正确选择"。命名要能自解释，描述要说明使用时机而非仅仅说明功能，参数要避免歧义（"日期"要说清格式）。这三点决定了工具调用的准确率上限，而准确率上限决定了智能体能否被信任。
