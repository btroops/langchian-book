# 第 22 章　如果你从零设计一个 Harness

> 把全书原理压成一份设计清单和一张决策矩阵。这一章的目标是：读完就能开评审会。

## 引子

假设现在有一个任务：为团队设计一套智能体运行框架。可能因为要自研，可能因为要评估现成方案，也可能因为要在现有框架上做深度定制。

第一个问题是"从哪开始"。多数人的第一反应是"先看看别人怎么做"——然后被十几个方案的架构图淹没。第二个问题是"怎么判断某个设计对不对"，因为每个方案都能讲出一套道理。

这一章提供两个工具来回答这两个问题。**一份设计清单**，用来确保没有漏掉必须回答的问题；**一张决策矩阵**，用来在"自研还是用现成"之间做理性判断。清单和矩阵都直接来自前面二十一章的原理，没有新概念——**这就是第二十一章之后仍然需要这一章的原因：原理本身不会自动变成可执行的设计动作。**

## 五个必答设计题

这五个问题必须在动工前回答清楚。它们不是"最好想一下"，而是"含糊其辞就一定会返工"。

**第一题：状态放在哪里，包含什么？**

要回答的子问题：状态的作用域是什么（单次执行 / 一次会话 / 长期用户）？状态里放数据还是放引用？每个字段的合并语义是什么（第 11 章）？状态如何序列化？

**含糊的代价：** 如果状态作用域没定清楚，会在多会话场景下出现状态串味；如果合并语义没定清楚，会在并发时丢数据；如果放进了不可序列化的东西，会在启用持久化时全部失败。这三类问题都在上线后才暴露。

**第二题：控制流由谁决定？**

要回答的子问题：执行路径是完全预定义的，还是运行期决定的？允许循环吗？循环的终止判据是什么（第 20 章）？谁负责判断"无法完成"？

**含糊的代价：** 如果没有明确的终止判据，系统在困难任务上会无限尝试而不是失败；如果没有"无法完成"这个出口，失败会被伪装成长时间运行。

**第三题：怎么持久化？**

要回答的子问题：需要保存的粒度是什么（超步 / 关键节点）？会话标识的粒度是什么（第 13 章）？恢复时如何处理版本不一致？副作用如何保证幂等？

**含糊的代价：** 粒度太粗导致恢复时大量重复执行；会话标识定义错误导致历史无法关联；幂等缺失导致恢复时重复触发外部动作。**这一题含糊的代价是最高的，因为它的事故通常涉及资金或数据。**

**第四题：工具怎么接？**

要回答的子问题：工具来源是本地还是远程？用哪种协议（第 17 章）？工具失败如何表达（结构化返回还是异常）？工具集大小是否受控？工具的结果如何裁剪？

**含糊的代价：** 工具集失控导致调用准确率下降；失败用异常表达导致模型失去自我修正机会；返回不裁剪导致上下文被单次调用吃光。

**第五题：怎么观测？**

要回答的子问题：埋点覆盖哪些内容（第 18 章的六项）？数据保留策略是什么？是否支持回放（回放需要输入输出完整、结构明确、可注入）？是否有分层评估指标？

**含糊的代价：** 前四题做对但这一题没做，系统的表现会像"黑箱"，任何问题都无法归因。**这是最容易被推迟、也最容易事后追悔的一题。**

## 设计清单（按模块）

下面这份清单可以直接作为设计文档的目录。每一项后面括号里是"不做会怎样"——这是判断某项是否真的必要的依据。

**状态模块**

- 状态字段清单，每个字段的类型、含义、单位（不做：字段含义靠猜，模型填错无感知）
- 每个字段的归约语义（不做：并发写丢数据）
- 状态的序列化验证（不做：启用持久化时才发现不可序列化）
- 状态体积上限与超限处理（不做：检查点与传输成本失控）
- 状态的可解释性检查：只看状态能否说出任务进展（不做：事故时无法归因）

**控制流模块**

- 正常终止判据（不做：任务无法收敛）
- "无法完成"的显式出口（不做：无解任务持续消耗预算）
- 步数、工具调用数、token、时长四类预算（不做：极端路径导致账单暴涨）
- 进展检测机制（不做：原地打转不被识别）
- 条件分支的兜底路径（不做：静默挂起）

**持久化模块**

- 检查点粒度与保存内容（不做：恢复时重复执行过多）
- 会话标识定义（不做：多会话状态串味）
- 中断信息结构：待决问题、上下文、权限与时效、幂等标识、版本（不做：恢复方不知道要提供什么）
- 幂等键设计（不做：重复触发副作用）
- 版本兼容策略：流程变更时在途任务如何处理（不做：恢复旧任务时报错或错乱）

**工具模块**

- 工具四项抽象完整：身份、描述、参数、结果语义（不做：模型调用准确率低）
- 失败作为结构化返回值（不做：模型无法自我修正）
- 工具集大小与可区分度审查（不做：工具误选率上升）
- 结果裁剪与结构化提取（不做：上下文被单次调用吃光）
- 权限分级：读写分离、副作用工具单独管控（不做：越权与滥用）
- 外部内容边界标记（不做：注入风险）

**观测模块**

- 六项关键埋点（不做：问题无法归因）
- 失败案例全量保留、成功采样（不做：观测成本失控或关键数据缺失）
- 回放能力（不做：问题无法复现）
- 分层评估指标（不做：指标下降时无法定位）
- 回归集与标注（不做：改动效果无法客观比较）

**安全与治理模块**

- 权限校验（工具级 + 恢复接口级）（不做：越权操作）
- 不可逆动作的审批条件（不做：误操作无法挽回）
- 预算在线检查与中止（不做：超支）
- 提示注入的防御：内容与指令的边界（不做：外部内容被当指令执行）
- 行为定义的灰度与回滚流程（不做：变更风险不可控）

## 决策矩阵：自研还是用框架

这是评审会上最常被争论的问题。用一张矩阵把它变成可讨论的判断。

| 维度 | 倾向于用现成框架 | 倾向于自研 |
|---|---|---|
| 需求形状 | 与框架提供的能力高度重合 | 存在框架无法表达的核心需求 |
| 团队能力 | 缺少相关基础设施经验 | 有分布式系统与运行时经验 |
| 时间约束 | 需要快速验证与上线 | 有足够周期且愿意投入 |
| 变更频率 | 业务流程相对稳定 | 流程频繁变化，需要极致灵活性 |
| 规模 | 请求量小到中等 | 规模大到需要针对性优化 |
| 依赖治理 | 接受引入依赖树 | 对依赖有严格管控要求 |
| 可迁移性 | 接受的绑定范围可承受 | 需要跨平台、跨云的可迁移性 |
| 差异化 | 该能力不是竞争差异点 | 该能力是核心竞争力 |

**使用方法：逐项判断，数一下两列各占多少。** 不需要追求所有项都指向同一侧——但在做决定之前，必须对每一项都给出明确判断。含糊的项往往就是未来的风险点。

有一个特别值得警惕的组合：**"核心差异化" + "需求与框架能力重合"**。这意味着你的核心竞争力构建在别人的抽象之上，一旦框架的演进方向与你的需求分化，你会非常被动。这种情况下，即使短期用框架更快，也应该规划一条下探到低层原语的路径。

反过来，**"非差异化" + "需求重合" + "时间紧张"** 是最清晰的"直接用框架"信号。这种情况下自研几乎肯定是浪费。

## 主流方案的定位对比

不需要比较功能列表，只需要回答一个问题：**它把什么当成一等对象，愿意替你做多少决定。**

| 方案类型 | 一等对象 | 替你做的决定 | 主要适用 |
|---|---|---|---|
| 高层智能体框架 | 标准工具调用循环 + 中间件钩子 | 循环结构、状态组织、默认行为 | 快速构建常规智能体，需求与默认行为接近 |
| 低层图运行时 | 状态、节点、边 | 调度与持久化，不决定流程 | 需要完全控制控制流与恢复能力 |
| 多智能体编排框架 | 智能体角色与协作关系 | 通信机制与协作拓扑 | 任务天然可拆分为角色分工 |
| 纯自研 | 由你定义 | 无 | 需求特殊、需深度可控、或有强可迁移性要求 |

选择时的实用建议：**先问"我的需求与这个方案的默认行为差多远"。** 差距小，用它最划算；差距大，你会一直在和默认行为对抗，这时下探到低层原语（或者自研）反而更省力。**"和框架搏斗"是选型失败最典型的症状——它通常不是框架不好，而是抽象层级选错了。**

## 演进路线

不要一次建完。按阶段演进的关键是**每个阶段都解决当下真实存在的问题**，而不是为想象中的需求预留。

**阶段一：最小可用。** 单智能体、无持久化、无中断、基础观测（至少记录模型调用的输入输出与工具调用）。

这一阶段要回答的问题：任务能不能做成？质量是否可接受？成本大概在什么量级？

**阶段二：稳定性。** 加入失败语义（重试与回退）、契约校验、预算控制、结构化评估集。

这一阶段要回答：失败率有多少？主要失败模式是什么？

**阶段三：长时与可恢复。** 引入持久化、检查点、中断恢复、幂等设计。触发条件是"出现了需要跨请求存活的任务"或"出现了人工介入需求"。

这一阶段要回答：恢复的正确性如何保证？副作用如何避免重复？

**阶段四：规模化与治理。** 加入分层评估、回放能力、灰度发布、权限分级、成本配额。

触发条件是"多团队使用"或"上了关键业务"。

**演进的关键判断是"什么时候进入下一阶段"。** 判断依据不是"下一阶段听起来更好"，而是"当前阶段暴露了哪个具体的、无法在当前阶段解决的问题"。**没有具体问题的升级都是过度设计。**

## 三个最容易踩的架构陷阱

**陷阱一：把运行时问题当成组件问题。**

症状：想用"加一个组件"的方式解决循环、恢复、中断这类需求。表现是出现大量"包装器"、大量跨组件的隐式约定、以及每次新增需求都要改动核心循环。

根源与纠正：第 4 章讲过这个判断——当需求开始要求"跨步骤的、可持久化的、可恢复的"保证时，它就是运行时问题。纠正方式是停下来升级执行模型，而不是继续加组件。

**陷阱二：观测留到最后做。**

症状：功能都做完了，"顺便加个日志"。上线后发现问题无法定位，或者发现需要观测的数据没有被记录（因为采集点需要侵入业务代码）。

根源与纠正：**观测的采集点必须在协议层。** 这也是为什么要尽早确定执行协议（第 5 章）——协议一旦确定，观测就有了统一的挂点；协议之后再补，成本会成倍增加。

**陷阱三：假设模型会按设计者的意图行事。**

症状：系统里到处是"模型应该会……"的隐含假设。比如"模型应该会按格式输出""模型应该会在信息不足时说不确定""模型应该不会重复调用同一个工具"。

根源与纠正：这些假设在多数情况下成立，所以测试时不会暴露。正确的姿态是**把每一个假设都变成显式的约束或检查**：假设格式会正确 → 加校验；假设会承认不确定 → 在提示中定义这个行为并检查；假设不会重复调用 → 加重复检测。

## 常见误区与排查

- **"先建一套完整框架，以后需求都能覆盖"** → 症状：框架做完了，第一个真实业务跑不通，需要大量改造。根因：在没有真实需求约束的情况下设计抽象。修法：按演进路线分阶段，每阶段由真实问题驱动。
- **"照抄某个知名方案的架构"** → 症状：抄来的结构与自己的业务语义不匹配，到处打补丁。根因：忽略了架构是对特定问题的回答。修法：先写清自己的五个必答题答案，再对照别人的答案做取舍。
- **"观测等上线前统一加"** → 症状：需要的数据没被记录，只能重新发版再等数据。根因：观测是横切关注点，采集点需要提前设计。修法：在执行协议确定时就把埋点确定下来。
- **"自研能省掉依赖的麻烦"** → 症状：自研后发现重写了重试、序列化、并发合并、token 计数。根因：忽略了这些是必须解决的问题，不会因为自研而消失。修法：决策矩阵中计入这部分成本。
- **"性能问题以后优化"** → 症状：优化时发现瓶颈在数据模型上（状态太大、字段设计导致无法裁剪）。根因：数据模型是难改的底层决定。修法：状态设计阶段就考虑体积与裁剪需求。
- **"灰度发布可以后期再加"** → 症状：提示与模型的变更无法安全上线，只能半夜发布全量。根因：缺少分流与回滚能力。修法：在进入"关键业务"之前就把灰度能力建好。

## 本章要点

- 五个必答设计题：状态放在哪里包含什么、控制流由谁决定、怎么持久化、工具怎么接、怎么观测。含糊即返工。
- 设计清单按六个模块组织（状态、控制流、持久化、工具、观测、安全治理），每项标注了"不做会怎样"，这是判断必要性的依据。
- 决策矩阵的八维度中，最该警惕的组合是"核心差异化 + 需求与框架重合"；最清晰的"直接用框架"信号是"非差异化 + 需求重合 + 时间紧"。
- 方案选择只问一个问题：它把什么当成一等对象。选型失败最典型的症状是"和框架搏斗"，根因通常是抽象层级选错。
- 演进分四阶段：最小可用、稳定性、长时与可恢复、规模化与治理。进入下一阶段的依据是"当前暴露了无法解决的具体问题"，而不是"下一阶段更好"。
- 三个最容易踩的陷阱：把运行时问题当组件问题、观测留到最后做、假设模型会按设计者意图行事。
- 每一个"模型应该会……"的假设，都应该被转成显式的约束或检查。

## 迁移视角：如果不用这个框架

这一章的两份工具（必答题清单与决策矩阵）可以直接用于任何"自研还是引入"的决策，不只限于智能体。

**关于清单的价值：** 设计评审里最有效的提问不是"你觉得这个方案怎么样"，而是"这五个问题你们的答案是什么"。前者引出观点，后者引出事实。**把主观评审变成对必答题的逐项回答，是提高评审效率最直接的办法。**

**关于决策矩阵的价值：** "自研还是买"这类问题之所以经常争论不休，是因为双方在比较不同的维度——一方说"自研可控"，另一方说"采购更快"，两个论点都对，但没有可比性。矩阵的作用是**把所有维度摆到同一张表上**，让取舍可以被看见、被记录、被复盘。真正有价值的不是矩阵算出的总分，而是**在填表过程中被迫做出的那些明确判断**——它们会成为未来复盘时"当初为什么这么选"的依据。

最后一条是关于设计顺序的经验：**先写"不做什么"，再写"做什么"。** 本章清单里"不做会怎样"这一列就是为此设计的。理由很实在：一个系统的复杂度上限由它拒绝承担的责任决定。**能把减法做清楚的设计，才有机会稳定。**
