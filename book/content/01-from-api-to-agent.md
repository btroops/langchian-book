# 第 1 章　从「调用模型」到「编排智能体」

> 框架不是被发明出来的，是被问题逼出来的。搞清楚"哪些问题逼出了哪一层抽象"，比记住 API 名称有用得多。

## 引子

先看一个几乎每个团队都经历过的场景。

某团队要给客服系统加一个智能问答能力。第一天的想法很朴素：把用户问题拼进一段提示，发给模型，把返回的文本显示出来。半天就做完了，演示效果还不错。

第二周产品提需求：回答必须基于内部知识库。于是加一步检索，把命中的文档塞进提示。还能做。

第三周要求"查订单状态"。模型不知道订单在哪，必须让它调用内部接口。于是引入工具调用。到这里，代码里出现了第一个循环：模型要求调工具 → 宿主执行 → 结果回灌 → 模型继续。如果模型又要求调另一个工具呢？循环得能继续。

第四周，客服主管要求"金额超过 5000 的退款必须人工确认"。于是循环里多了一个中断点：跑到一半停下来等人。那么停下来的状态存在哪？如果客服半小时后才点确认，进程还活着吗？

第五周，有人发现有些对话会转十几轮工具调用，最后给出一个看似合理但完全错误的答案。需要能回放整条执行路径，看清是哪一步走歪的。

到这里，最初"拼个提示发出去"的东西，已经变成了一套需要**状态管理、循环控制、持久化、中断恢复、执行追踪**的系统。这不是 LangChain 发明的需求，这是任何生产级 LLM 应用都会撞上的同一堵墙。

这一章要回答的就是：这堵墙的每一块砖分别是什么，以及它们为什么必须存在。

## 三次抽象跃迁

从最原始的模型调用到一个可用的智能体，中间隔着三次抽象跃迁。每一次跃迁都不是审美选择，而是被上一阶段的失败逼出来的。

**第一次跃迁：从"调用"到"编排"。** 一旦系统里出现了提示模板、模型、输出解析、检索器这几类角色，就需要一个统一的方式来描述"它们怎么串起来"。这里的关键词是**可组合**。如果每个组件都有自己的调用方式，那么两两组合就要写一次适配代码，三三组合就要写更多——组合的成本随组件数量呈平方级增长。这是所有框架化努力的最初动机。

**第二次跃迁：从"编排"到"循环"。** 编排的本质是流水线：数据从这头进，从那头出，路径在执行前就已经确定了。但智能体的核心特征是**下一步做什么取决于上一步的结果**。检索没找到有用信息？换个查询词再来一次。工具返回的参数错了？重新组织一次调用。这种"根据中间结果决定后续路径"的能力，无法用一条预先定好的流水线表达。

**第三次跃迁：从"循环"到"可恢复运行时"。** 循环带来了一个隐蔽但致命的问题：它是有状态的，而且是长时间运行的。一旦执行过程可能跨越数分钟甚至数天（因为要等人审批），那么进程崩溃、部署重启、用户关掉页面都会导致中间状态丢失。于是必须引入**持久化**——把执行过程本身变成可存储、可恢复的数据。

这三次跃迁对应了本书的三大板块：第二部分讲编排（LangChain 的 Runnable 与 LCEL），第三部分讲循环与持久化（LangGraph），第四、五部分讲支撑这一切的契约、协议与可迁移的设计原理。

## 朴素实现的失败清单

如果不用框架，直接手写，会依次撞上哪些问题？下面这张清单来自大量实际项目的共同经验。它的价值在于：**每一条都对应框架里的一层抽象**。

| 失败现象 | 直接后果 | 对应的抽象 |
|---|---|---|
| 上下文没有统一管理 | 多轮对话后模型"忘记"前文，或提示无限膨胀撞到窗口上限 | 状态（State）/ 消息历史 |
| 循环没有终止条件 | 两个工具互相调用，无限循环，账单失控 | 终止判据 / 跳数预算 |
| 调用失败没有重试与回退 | 一次网络抖动，整条链路抛错，用户体验断裂 | 失败语义（回退/重试/超时） |
| 中断后状态丢失 | 用户审批耗时较长，重启后必须从零开始 | 检查点（Checkpoint） |
| 参数直接拼进提示 | 用户输入里的特殊字符污染指令结构，行为异常 | 模板与变量绑定 |
| 模型输出直接当数据用 | 一个格式偏差导致下游解析崩溃，但没有定位线索 | 输出解析器 / Schema 校验 |
| 工具返回结果无边界 | 日志里几百 KB 的原始响应塞进提示，成本与噪声齐升 | 结果裁剪 / 契约化 |
| 执行过程不可观测 | 出错只能看到最终回答，无法判断是哪一步走歪 | 回调与追踪（Trace） |

值得强调的是最后一条。前七条都是"功能坏了"，最后一条是"你没法知道为什么坏"。在确定性系统里，出错总能在日志里找到异常栈；但在概率性系统里，执行成功、格式合法、结果却是错的——这种失败只有拿到完整执行轨迹才能诊断。

## 一次事故的解剖

把上面几条串起来看，会更清楚为什么"只是加个循环"会失控。

设想一个退款处理 Agent。用户提出诉求，模型决定调用"查询订单"，得到订单号后再调用"发起退款"。整个流程看起来只有两步，很安全。

但实际发生的是这样一条路径：模型先查询订单，返回的订单状态里包含多个子订单；模型决定逐个核查，于是连续调用了五次订单查询；其中一次返回了"已发货"；模型试图调用"修改地址"工具，参数里带了一个不存在的地址 ID；工具报错，模型重新尝试，参数依然错误；模型转而要求调用"取消发货"；取消失败，模型重新回到订单查询——形成回边；在第六次循环时，上下文已经累积了八次工具调用的完整返回内容，接近窗口上限；模型开始在长上下文中丢失最初的用户诉求，最终生成了一个"已为您取消订单并退款"的答复，而实际上什么都没发生。

这条路径暴露了四个独立的问题：

**不可终止。** 没有任何机制判断"这个任务已经陷入了无进展的循环"。
**状态污染。** 工具返回的原始数据无节制地堆积在上下文里，挤掉了真正重要的信息——用户最初的要求。
**副作用不可控。** "取消发货"这类动作一旦执行就无法撤销，但模型是在试错心态下调用的。
**不可复盘。** 如果没有完整轨迹，事后只能看到一句自信的错误答复，无法还原决策过程。

这四个问题分别对应第三部分的终止控制、第四部分的契约与裁剪、第十四章的人在回路、第四部分的观测能力。**框架的价值不在于它提供了函数，而在于它把这些问题的解法固定成了结构。**

## 抽象税：框架给了什么，又拿走了什么

框架从来不是免费的。"用了框架代码变少"这个印象常常是错觉——代码可能只是从你的文件挪进了框架的内部。要诚实地算这笔账。

框架给的三样东西：**结构约束**（强制你把状态、控制流、副作用显式声明出来，而不是散落在各处）、**已解决的边界问题**（重试、序列化、并发合并、中断恢复这些琐碎但容易写错的地方）、**一致性**（团队里所有人都用同一套心智模型读代码）。

框架拿走的三样东西：**控制权**（执行循环由框架驱动，你只能通过钩子介入）、**可见性**（出错时错误栈里一半是框架内部帧，排查路径变长）、**升级自由**（你和一个具体版本的实现绑定了，它的行为变更会传导到你身上）。

一个实用的判断方法：**当框架解决的问题比它引入的约束更贵时，用它；反之不用。** 如果你的系统只是一次检索加一次生成，没有循环、没有中断、不需要恢复，那么自己写五十行代码比引入一整代抽象更划算。抽象税是真实的，只有在摊薄到足够的复杂度上才划算。

## 什么时候不该用框架

这一节可能和本书的主题有点别扭，但它是必要的。

不用框架的信号：执行路径在编译期（写代码时）就完全确定，不存在"根据中间结果改变路径"；单个请求的生命周期在秒级，崩溃了重试一次也无所谓；不需要人工介入；团队里只有一两个人在维护；以及最重要的一条——你对运行时行为的每一个细节都必须精确掌控，容不下任何框架的默认行为。

用框架的信号：出现了循环；出现了需要等待人类的暂停；需要从任意中间点恢复；需要多人协作并共享一套状态定义；需要把执行过程作为可分析数据来用。

这两组信号的分界，其实就是第 10 章要讲的"链"和"图"的分界。

## 常见误区与排查

- **"先写出来，架构以后再说"** → 症状：第三周开始每个新需求都要改动核心循环，改动互相冲突。根因：状态和控制流没有显式声明，而是隐含在代码流程里。修法是先把状态结构写下来，再写逻辑。
- **"模型变强了，这些工程问题会消失"** → 症状：换了更强的模型，工具调用变准了，但无限循环、上下文爆炸、无法恢复这三类问题一个都没少。根因：它们不是模型能力问题，是系统架构问题。
- **"框架会帮我把状态管理好"** → 症状：状态字段越加越多，含义越来越模糊，不同节点对同一字段的理解不一致。根因：框架只提供状态的容器与合并机制，**状态应该包含什么，仍然是设计责任**。
- **"能跑通就说明设计对了"** → 症状：测试环境全绿，线上偶发错误答复。根因：概率性系统的失败是分布式的，单次通过不构成正确性证据。必须靠轨迹评估而不是靠跑通。
- **"工具越多能力越强"** → 症状：模型在二十个工具里选错，或者反复调用同一个工具。根因：工具集扩大提升了决策难度，工具的"可区分度"比数量重要得多。

## 本章要点

- 框架是被问题逼出来的：编排成本、循环控制、状态持久化、执行可观测，四个问题依次逼出四层抽象。
- 三次跃迁的顺序是刚性的：先统一组件协议，再引入循环，再引入持久化。跳步会导致返工。
- 朴素实现的八类失败，每一类都对应框架的一层抽象；能对上号，就说明你看懂了抽象存在的理由。
- 智能体失控的典型形态不是报错，而是"成功执行并给出错误答案"，这只有轨迹级观测才能发现。
- 抽象税是真实的：结构约束、边界问题解法、团队一致性是收益；控制权、可见性、升级自由是成本。
- 判断标准：当系统出现循环、中断、恢复、多人协作中的任意一项时，框架才开始划算。
- 模型能力提升解决不了架构问题。这三类问题（不可终止、状态膨胀、不可恢复）与模型强弱无关。

## 迁移视角：如果不用这个框架

把这一章的结论从 LangChain 语境里抽出来，它说的是任何"长时运行、有状态、需要与外部世界交互"的系统都必须具备的四件东西：**显式状态、显式控制流、持久化边界、观测通道**。

在传统后端里，这四个东西早就有了别的名字：状态对应会话存储或工作流实例；控制流对应状态机或编排引擎（例如工作流编排、Saga 模式）；持久化对应事务日志与事件溯源；观测对应分布式追踪。LLM 应用并没有发明这些概念，它只是把一个原本用于分布式系统的工程问题，压缩到了一次请求的生命周期里。

所以当你在 LangGraph 里看到检查点、超步、归约器这些词时，不必视之为新物种。它们是分布式系统里早已成熟的模式，被移植到了一个输入输出都不确定的环境里。理解这个对应关系，你就能在换技术栈时迅速定位自己站在哪个抽象层——也能在框架给出可疑设计时，判断它是不是违背了这些模式多年积累的经验。
