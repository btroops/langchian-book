# 第 17 章　协议层：工具与智能体的标准化

> 协议化把 M×N 的集成问题变成 M+N。代价是抽象损耗，收益是任何一方都可以独立演进。

## 引子

一个团队要让智能体接入内部系统：订单、库存、工单、财务、CRM。第一版的做法是给每个系统写一个工具包装，很快五个工具就完成了。

问题出现在第二个月。团队换了模型供应商，新模型对工具描述的表达方式有要求，五个包装都要调整。第三个月，公司要上线另一个智能体产品（客服助手），需要复用其中三个工具，但那个产品的技术栈不同，包装代码不能直接用，于是重写。第四个月，某个内部系统升级了接口，两套包装都要改。

这就是**组合爆炸**的具体样子。问题不在于麻烦，而在于**维护成本随"使用方数量 × 提供方数量"增长**。五个系统、两个使用方、两个模型供应商，理论上就有二十种组合需要维护。任何一处的变动都会产生多个修改点，而每个修改点都是引入不一致的机会。

协议化就是解决这个问题的标准手段：**约定一个中间格式，让提供方只实现一次，使用方只实现一次。** 提供方与使用方的耦合被"提供方到协议"和"协议到使用方"两次转换替代，两个转换各自独立演进。

这一章讲这套协议层的设计原理：标准化的核心抽象是什么、能力模型怎么组织、以及协议化本身的代价在哪里。

## 工具标准化的核心抽象

无论哪个协议，工具描述的核心抽象都是同一组四项。理解这四项，就理解了所有工具协议的骨架。

**第一项：身份。** 工具需要一个标识，让它能被唯一引用。看起来简单，但有两个坑：**命名冲突**（两个来源都提供了叫 `search` 的工具）和**命名稳定性**（改了名字，所有依赖它的记录都会失效）。实用做法是在命名里带上来源前缀，并且把名字当接口对待，不轻易改动。

**第二项：语义描述。** 说明这个工具做什么、什么时候该用、什么时候不该用。第 7 章讲过，这份描述是提示的一部分，直接决定模型的调用准确率。协议里这一项通常是一个自然语言文本字段，但对它的要求应该比"随便写写"高得多——它是工具可用性的主要决定因素。

**第三项：参数结构。** 参数的名字、类型、必填性、约束。这一项与第 16 章的 Schema 完全对应，是工具调用可靠性的物理基础。

**第四项：结果语义。** 结果的结构，以及**错误的表达方式**。第四项最容易被简化处理，但它决定了模型在失败时的行为质量。一个只返回"执行失败"的错误，模型只能盲目重试；一个返回"参数 `order_id` 格式不正确，应为 16 位数字"的错误，模型有机会自行修正。

| 抽象项 | 作用 | 常见缺陷 |
|---|---|---|
| 身份 | 唯一引用与稳定引用 | 命名冲突、改名导致记录失效 |
| 语义描述 | 决定模型调用准确率 | 写成功能罗列，未说明使用时机 |
| 参数结构 | 决定调用参数的正确率 | 单位与格式未声明；枚举值不完整 |
| 结果语义 | 决定失败时的自我修正能力 | 错误信息过于笼统，模型只能盲试 |

**"结果语义"这一项值得单独强调。** 工具协议里有一个很容易被忽略的设计：**工具执行失败应该是一种正常返回值，而不是异常。** 因为失败的消费方是模型，它需要把失败信息纳入下一步推理。如果失败以异常形式抛出并中断流程，模型就失去了修正的机会——它只能看到"任务失败了"，而不是"哪里错了、怎么改"。

所以工具的返回通常有两种形态：成功的结果、以及结构化的失败说明。**把失败设计成数据而不是控制流，是让智能体具备自我修正能力的前提。**

## MCP 的能力模型

模型上下文协议（MCP）是目前工具标准化方面最被广泛采纳的协议。它的设计值得分析，因为它体现了一套完整的"能力如何标准化"的思路。

**它是客户端-服务器结构。** 提供能力的一方是服务器，使用能力的一方是客户端。这个方向不能搞反——能力由提供方定义并暴露，使用方按需连接。

**它分三类原语，区别在于"谁主导"。**

**工具**是由使用方（模型）主导的：模型决定调用哪个、传什么参数。这对应"我要做一件事"。

**资源**是由提供方主导的：服务器暴露一些可读取的内容，由使用方选择读取哪些。这对应"我要看一份材料"。把"读"从"做"里单独分出来，是有意义的设计——因为读操作是只读的、幂等的、通常更安全，不需要像写操作那样配置审批。

**提示模板**是由提供方提供的预制交互模式：服务器可以提供一些经过设计的交互入口，让使用方直接使用。这对应"我要按某种标准流程交互"。这一类原语的价值在于把领域知识标准化下来，而不是让每个使用方都从零设计提示。

**为什么区分这三类而不是统一成一个"能力"？** 因为它们的**风险与治理要求不同**。读操作可以放开，写操作需要控制；预制交互模式是低风险的（它是建议性的），模型自主决策是高风险的。把它们分开，协议就能对每一类施加不同的约束——**这是"按风险分级"这个工程原则在协议设计里的体现。**

**协议还包括能力协商。** 连接建立时，双方声明各自支持哪些能力与特性。这个机制的价值在于**向前兼容**：新版本可以引入新能力，旧实现只使用双方都支持的交集。这是所有需要长期演进的协议都必须具备的机制——没有它，任何一方升级都会破坏已有的连接。

## 传输与生命周期

协议需要规定能力"怎么传"，这部分的取舍直接影响部署形态。

**本地进程传输。** 提供方作为本地子进程运行，通过标准输入输出通信。优点是简单、低延迟、无网络配置、天然处于同一安全域。缺点是只能本机使用、生命周期与宿主绑定、不适合需要独立伸缩或独立部署的场景。

**基于网络的传输。** 通过 HTTP 通信，支持流式响应。优点是提供方可以独立部署、多使用方共享、便于统一鉴权与审计。缺点是引入了网络故障、延迟、认证等一整套问题。

这两种的选择依据很直接：**能力是宿主的私有组成部分，还是组织级的共享资源？** 私有组件用本地进程更简单；组织级共享资源必须独立部署，否则升级、权限、审计都无法集中管理。

**生命周期管理**是协议里容易被低估的部分，有三件事需要明确。

**连接的建立与初始化。** 双方握手、协商能力、确认版本。这一步失败必须有明确的错误，而不是进入一个"连接上了但什么都做不了"的模糊状态。

**连接的健康与重连。** 网络传输下连接会断。协议需要定义断线后的行为：是自动重连并恢复状态，还是要求使用方显式重建？**在长时任务场景里，这个决定很重要**——一个跨小时的流程中途因为连接抖动而失败，用户体验会很差。

**连接的资源边界。** 一个使用方能否同时连接多个提供方？能连多少个？每个提供方的能力列表是否需要缓存？在能力可以动态变化的情况下，缓存与刷新的策略必须明确。

## 智能体间协议的设计分歧

除了"模型与工具"之间的协议，还有一类"智能体与智能体"之间的协议。这类协议的分歧比工具协议大得多，因为它要回答一个更根本的问题：**协作的单位是什么？**

**一种思路是任务导向。** 协作的单位是一个"任务"：委托方提交一个任务描述，受托方执行并返回结果，过程中可以上报进度。这种设计适合**目标明确、可异步执行**的场景——比如"帮我分析这份财报"或者"帮我处理这个工单"。它与第 13 章的长时执行、第 14 章的中断恢复天然契合，因为任务本身就是一个可持久化的对象。

**另一种思路是对话导向。** 协作的单位是一次交互回合：双方像人一样互相发消息、协商、追问。这种设计适合**信息不完整、需要澄清**的场景。它的缺点是状态难以界定（"这次对话什么时候算结束"），持久化与恢复也更复杂。

这两种思路的分歧，本质上是**"协作的原子单位是任务还是消息"**。任务导向更容易做可靠性保证（任务有生命周期、有状态、有终止），对话导向更容易做灵活性（可以自由追问）。实际系统常常是混合的：任务为外壳、对话为内部交互方式。

理解这个分歧有一个实用价值：**当你评估一个智能体协作方案时，先问它把什么当成一等对象。** 如果一等对象是任务，那么它应该能回答"任务如何持久化、如何中断、如何恢复、如何限制预算"。如果一等对象是消息，那么它应该能回答"会话如何界定边界、如何避免无限对话、如何在会话中间恢复"。**答不上来的部分，就是这个方案的短板。**

## 协议化的代价

协议化不是免费的，代价有四项，必须在评估时计入。

**代价一：抽象损耗。** 协议定义的是公共能力的交集，因此每个具体能力里总有一部分是协议表达不了的。这部分要么被丢弃（功能缩水），要么通过"协议内的自定义扩展"实现（复杂度回到协议外）。这个损耗不会消失，只能被管理。

**代价二：版本兼容的长期负担。** 一旦有了多个独立实现，任何协议变更都必须考虑"旧实现还在运行"。这会让演进速度受制于最慢的那个实现。协议的设计越早稳定，负担越小。

**代价三：调试链变长。** 一个工具调用失败，可能的原因分布在：使用方的参数构造、协议的序列化、网络传输、提供方的执行、提供方的错误包装、协议的解析。排查路径比直接调用长得多。**这是协议化的隐性成本，需要在工程上补偿**——通常靠追踪机制把整条链路串起来（第 18 章）。

**代价四：安全边界扩大。** 协议让能力可以被远程访问，也就把攻击面扩到了远程。三个具体风险需要正视：**权限问题**（提供方是否知道调用者是谁、有没有权限）、**注入问题**（工具返回的内容里如果包含指令性文本，模型可能把它当指令执行）、以及**能力滥用**（一个高权限的工具被模型在错误的场景下调用）。

**关于注入风险，有一条重要的设计原则：工具返回的内容是数据，不是指令。** 在协议层面，返回内容应该有明确的"这是外部内容"标记，并且在提示装配时被包裹与声明（第 8 章的结构边界）。**永远不要假设返回内容是安全的**——一个被污染的数据库、一条恶意构造的记录，都可能通过工具返回把指令带进模型的上下文。

## 常见误区与排查

- **"工具协议只要参数对就行，描述随便写"** → 症状：模型选错工具、在相似工具间来回试。根因：语义描述是提示的一部分，被当成了注释。修法：把描述当成提示工程来写，说明使用时机与边界。
- **"工具失败应该抛异常中断流程"** → 症状：模型无法自我修正，一次工具错误导致整个任务失败。根因：失败信息没有传递给模型。修法：把失败作为结构化返回值，包含错误原因与修正建议。
- **"所有能力都归到工具一类，简单"** → 症状：只读查询也被要求审批，或写操作缺少控制。根因：忽略了按风险分级的必要性。修法：区分只读与写入，对写入施加额外约束。
- **"连上就行，不需要能力协商"** → 症状：升级某一方后出现"调用不存在的功能"或行为异常。根因：缺少能力与版本的显式协商。修法：连接时声明各自支持的能力，只使用交集。
- **"工具返回的内容可以直接拼进提示"** → 症状：模型执行了返回内容里夹带的指令。根因：把外部内容当成了可信指令。修法：明确包裹与来源标注，并在指令中声明只按用户与系统消息行动。
- **"用远程协议总是比本地进程好"** → 症状：为了一个宿主私有能力引入了服务部署、鉴权、网络故障处理。根因：没区分私有组件与共享资源。修法：按能力的归属范围选择传输方式。

## 本章要点

- 协议化解决的是"使用方数量 × 提供方数量"的组合爆炸；收益是任一方可独立演进，代价是抽象损耗与长期兼容负担。
- 工具标准化的四项核心抽象：身份、语义描述、参数结构、结果语义。其中结果语义决定模型能否自我修正。
- 工具执行失败应该是**结构化返回值而不是异常**，把失败设计成数据是自我修正能力的前提。
- 能力原语按"谁主导"和"风险等级"分类（工具 / 资源 / 预置交互模式），分类的价值在于可对不同风险施加不同治理。
- 能力协商是所有长期演进协议的必备机制，它提供向前兼容。
- 传输方式的选择依据是"能力属于宿主私有组件还是组织级共享资源"。
- 智能体间协议的根本分歧是"协作的原子单位是任务还是消息"；任务导向更易做可靠性保证，对话导向更灵活。
- 协议化的四项代价：抽象损耗、版本兼容负担、调试链变长、安全边界扩大。其中注入风险必须靠"外部内容是数据不是指令"这条原则来防。

## 迁移视角：如果不用这个框架

协议化这件事在软件史上有大量先例，可以借用的经验很多。

**数据库驱动、HTTP、消息队列协议**都解决过同一个问题：把 M×N 变成 M+N。它们共同的教训是——**协议的成功取决于它定义得够小。** 定义越小，越容易实现、越容易稳定、抽象损耗越小。协议一旦贪大，就会在每次修订时面临"要不要破坏兼容"的痛苦选择。

**能力协商机制**在 TLS、内容协商、设备协议里都有对应物。它的通用原则是：**连接时先交换"我会什么"，再只使用交集。** 任何时候你想让两方独立演进，这个机制都是必需品。

**"失败是数据不是异常"** 这条原则的适用范围极广。任何"一方产出、另一方据此决策"的接口，都应该把失败信息作为正常返回值传递，因为消费方需要它来调整策略。把失败做成控制流（异常、中断），会把决策权从消费方手里拿走——这在自动化系统里往往是不利的。

**按风险分级治理**这条思路同样可以推广到任何"能力开放"的设计：读与写分开、幂等与非幂等分开、有副作用与无副作用分开。分级的价值在于**让治理措施精确定位到需要它的地方**，而不是对所有操作统一施加最严格的限制（那会让系统难用）或统一放开（那会留下风险）。

最后一条关于安全的原则值得单独记住：**任何跨越信任边界进入系统的内容，都必须被当作数据而不是指令。** 这在传统安全里早就是常识（SQL 注入、跨站脚本都是这个问题的不同形态），LLM 只是给它增加了一个新的入口——通过自然语言绕过指令与数据的边界。防御思路是一样的：**明确标记边界，并在解释时严格区分。**
