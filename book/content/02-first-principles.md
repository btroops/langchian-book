# 第 2 章　LLM 应用的第一性原理

> 所有架构决定最终都能回溯到四个物理约束。不理解约束，就只能靠模仿别人的架构来做事。

## 引子

问一个看起来很简单的问题：为什么 LLM 应用需要"外部记忆"？模型不是有上下文窗口吗，把历史都放进去不就行了？

这个想法在第一次做多轮对话时一定会出现，并且在头两次测试里表现得很好。然后它会以三种方式崩塌。

第一种，聊到第三十轮时，请求报错——上下文超了。你想裁剪，但裁掉哪一段？上一轮用户说的偏好，还是三轮前工具返回的那张表？没有依据可循。

第二种，你裁掉了开头几轮，模型忽然"忘了"自己是谁、在做什么任务——因为最初的系统指令和任务定义被你裁掉了。

第三种更隐蔽：你只是把检索到的文档从三篇变成十篇，回答质量不但没提升，反而下降了。模型开始引用不相关的段落，因为它被淹没在噪声里。

这三次崩塌指向同一件事：**上下文不是"越多越好"的容器，而是一份必须在有限预算下分配的资源**。而要理解这个预算为什么存在、该怎么分配，就得回到 LLM 的基本物理约束上。

这一章讲四个约束，以及从它们推导出的四个必需品。全书的后续内容，都可以看作是这四件事的具体实现。

## 约束一：Token 与上下文窗口

模型处理文本的单位是 token，不是字符也不是词。上下文窗口是一次调用中"输入 + 输出"的 token 总量上限。

这个约束的工程含义有四点，每一点都会在后续章节反复出现。

**第一，一切内容都对得上账。** 系统提示、对话历史、检索到的文档、工具返回的原始响应、模型自己的中间推理——它们共享同一个预算池。任何一处膨胀，都会挤压其他部分。这就是为什么"工具返回结果裁剪"不是一个优化项，而是一个必需品：一次不裁剪的接口响应可能吃掉整个预算。

**第二，超出窗口不会被优雅降级。** 超出就是报错。没有"模型自动忽略后半段"这种机制。所以系统必须在发送前就完成预算核算，这是一个**发送前的检查，不是发送后的处理**。

**第三，注意力是衰减的。** 即使内容在窗口之内，模型对不同位置的敏感度也不相同。经验规律是：开头与结尾的信息更容易被稳定使用，中间部分容易被忽略。这直接决定了两个设计——关键指令应该放在靠前或靠后的位置；检索结果不应该简单地"全都塞在中间"。

**第四，窗口大小不等于有效工作记忆。** 一个支持超长窗口的模型，在塞满长上下文后的推理质量，通常不如"用更少的、更相关的内容"的情况。窗口是物理容量上限，不是有效容量。

## 约束二：无状态

模型不记得上一次调用。每次请求都是一次独立的、从零开始的计算。

这句话听上去平淡，但它的推论非常强硬：**所有"记忆"都必须是外部构造的，并且在每次请求时被重新注入。**

于是"记忆"这个词在工程上被拆成了两件事：**存储**（把信息保存在模型之外的地方）和**装配**（在每次请求时，决定把哪些信息重新放回上下文）。存储是数据库问题，装配是上下文工程问题——后者是第 21 章的主题，也是区分一个能用的 Agent 和一个好用的 Agent 的关键。

无状态还带来一个容易被忽视的好处：**它是水平扩展的前提**。因为服务端不持有会话状态，任何一个实例都能处理任何一次请求。代价是状态必须外置，而这个代价恰好和"可恢复"的需求重合了——这是一个少见的、两全其美的设计点。

## 约束三：概率性

同样的输入，不保证同样的输出。这不是缺陷，而是模型的工作方式：它在每个位置采样。

概率性对系统设计有三层影响。

**第一层：契约必须显式。** 在确定性系统里，"我期望它返回一个包含 name 字段的对象"可以是口头约定。在概率性系统里，这个约定必须在代码里被强制检查，否则某一天模型返回了一个结构相似但字段不同的结果，系统就会在下游某处崩溃，而且崩溃点离出错点很远。第三层防线就是我们反复提到的 Schema 校验。

**第二层：失败是分布式的，不是点状的。** 一个百分之二的单步失败率听起来很低，但如果一条链路有二十步，整条链路的成功率大约是六成多。这就是为什么"每个组件都调好了"并不等于"整体可用"。也是为什么必须做**轨迹级评估**而不是抽样看几个例子。

**第三层：可复现性需要额外设计。** 排查问题时，你希望"用同样的输入重跑一遍，看到同样的过程"。但采样参数、外部工具的实时返回、系统时间都会破坏这一点。解决办法不是消除随机性（那会损失能力），而是**把执行过程本身持久化**——不重跑，直接回放。这是第 13 章检查点机制的另一层价值。

## 约束四：副作用不可逆与延迟不可忽略

前三个约束关于"模型"，第四个约束关于"世界"。

**副作用不可逆。** 模型可以随时"重新想一次"，但一次已发生的转账、一封已发出的邮件、一个已创建的工单，不能因为模型改了主意就当作没发生。这意味着**执行必须与决策分离**：模型负责提出意图，宿主负责在执行前施加控制（验证、审批、去重、限额）。这个分离是所有人在回路机制的根基——第 14 章讲的审批、确认、编辑三种模式，本质上都是"在不可逆动作之前插入一道人工闸门"。

**成本三要素。** 每一次调用都在消耗 token（钱）、时间（延迟）、以及并发额度。这三者互相约束：想减少延迟可以少放上下文，但可能降低质量；想提高质量可以多轮验证，但成本上升。所以"预算"是一个必须显式管理的概念，而不是事后看账单。

**延迟决定架构形态。** 一个人机交互的对话，可接受的等待是秒级；一个批量分析任务，可接受的是分钟级甚至更久。这个差异决定了同一个 Agent 应该被部署成交互式服务、后台任务、还是带队列的长时工作流。第 19 章会展开这一点，但根源在这里。

## 四约束的推论：四件必需品

把四个约束放在一起，结论几乎是自动浮现的。

| 约束 | 直接推论 | 必需品 |
|---|---|---|
| 上下文窗口有限且共享 | 必须做预算分配与内容裁剪，且在发送前完成 | **上下文装配器** |
| 模型无状态 | 记忆必须外置并在每次调用时重新注入 | **外部状态存储** |
| 输出概率性 | 契约必须显式校验；执行过程必须可回放 | **校验层 + 持久化** |
| 副作用不可逆、成本受限 | 执行需与决策分离；必须能暂停等人 | **中断机制 + 预算控制** |

这四件必需品，就是本书后面所有内容的骨架：第 8、21 章讲上下文装配与校验，第 11、13 章讲状态与持久化，第 14 章讲中断，第 12、19 章讲执行与预算。

有一个判据值得记住：**一件东西如果只在某些场景才需要，它是优化项；如果在所有场景都必须处理，它才是必需品。** 上面四件都属于后者。你可以在实现上偷懒不做，但处理它们的成本不会消失，只会被转移到运行时，以"上下文溢出""状态丢失""静默错误""重复副作用"这四种形态出现。这也是本书反复要区分的一对概念：**可以推迟的决策，和不可回避的约束。** 前者随需求变化，后者随模型的工作方式而定。

## 与 Web 服务的根本差异

很多人带着做 Web 服务的直觉来做 LLM 应用，然后在几个地方反复踩坑。把差异列清楚，可以少走一段路。

| 维度 | 常规 Web 服务 | LLM 应用 |
|---|---|---|
| 输出确定性 | 确定性，可以断言 | 概率性，只能统计评估 |
| 失败形态 | 异常、错误码，定位明确 | 静默错误，结果看似合理 |
| 单次请求耗时 | 毫秒到秒级 | 秒级到分钟级，甚至跨天 |
| 状态位置 | 数据库，请求内读写 | 请求之间持续存在，且会跨越进程重启 |
| 副作用 | 明确的事务边界 | 分散在工具调用中，需逐个施加控制 |
| 调试手段 | 日志 + 断点 | 需要完整执行轨迹回放 |
| 测试方式 | 单元测试覆盖率 | 数据集评估 + 回归基线 |
| 成本模型 | 主要是一次性硬件投入 | 随调用量与 token 线性增长 |

其中"静默错误"这一行最值得警觉。在 Web 服务里，一个返回 500 的接口是坏掉的接口；在 LLM 应用里，一个格式完美、语气自信、内容错误的回答，从系统角度看是"成功"的。**所以 LLM 应用的第一道防线不是测试，而是观测。**

## 常见误区与排查

- **"窗口越大，能放的历史越多，问题越少"** → 症状：上下文拉长后回答质量下降，模型开始答非所问。根因：把物理容量当成有效容量，忽略了注意力衰减与噪声干扰。修法是优先做筛选与压缩，而不是扩容量。
- **"无状态是缺陷，应该想办法让模型记住"** → 症状：试图把所有历史无差别注入，成本线性上升，效果却在某个点后不再提升。根因：没有区分"存储"与"装配"。存储可以无限，装配必须有取舍。
- **"链路每一步都很准，整体就没问题"** → 症状：单步评估漂亮，线上投诉不断。根因：忽略了失败率的乘法效应。修法：统计整条任务的端到端成功率，并优先削减步数。
- **"模型重试是安全的"** → 症状：偶发重复下单、重复发券。根因：重试的是包含副作用的执行，而不是纯计算。修法：把副作用调用单独标记出来，配幂等键与去重。
- **"成本是运营问题，不是架构问题"** → 症状：上线后账单远超预估，被迫临时砍功能。根因：预算没有进入设计阶段。修法：在链路设计时就标注每一步的 token 与延迟预算。

## 本章要点

- 上下文窗口是**共享预算**，不是独立容器；所有内容共用同一笔额度，且必须在发送前完成核算。
- 模型无状态，所以"记忆"必须拆成存储与装配两件事分开处理。
- 概率性的代价是失败分布式累积，因此端到端成功率和轨迹质量比单步指标更重要。
- 减少链路步数带来的收益，通常大于优化单步成功率。
- 副作用不可逆，所以决策与执行必须分离，不可逆动作之前必须能插入人工闸门。
- 成本三要素（token、延迟、并发额度）互相约束，预算必须显式设计。
- Web 服务的直觉在"静默错误"这一点上失效最严重：LLM 应用的第一道防线是观测，不是测试。

## 迁移视角：如果不用这个框架

这四个约束没有任何一条是 LangChain 或 LangGraph 特有的。它们来自模型本身的工作方式，因此无论你用哪个框架、用什么语言，它们都在那里。

换到别的技术栈时，你会发现同样的四件必需品换了名字出现：在云平台的托管智能体服务里，上下文装配叫"会话管理"，检查点叫"运行状态持久化"，中断叫"回调/审批流"；在自研系统里，它们可能就是一个数据库表、一个队列、一个状态机。

判断一个技术方案是否靠谱，有一个便宜的办法：把这四个约束当成检查表，看它在每一格上给出的答案是什么。凡是在某一格上给出"不需要处理"这种答案的方案，都值得警惕——不是因为它一定错，而是因为它多半在把成本延后到你上线之后才暴露。
